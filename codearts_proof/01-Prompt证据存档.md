# Prompt 证据存档（节选自真实会话）

> 以下为码道会话中**逐字复制的真实用户 Prompt**（含子智能体任务书），证明 Prompt 设计质量。
> 完整对话记录存于码道工作区 `~/.codearts/kernel/sessions/`，截图补录见 `02-截图清单与补录指南.md`。
> 【脱敏说明】原文中的密钥类内容仅以文件名/占位符出现（如 `{ENV:MIMO_API_KEY}`），无真实凭据。

## 证据 A：代码生成类任务书（会话 3 · sdk-engineer）

> **任务**：实现客户端 SDK 薄封装 autoRetry
>
> 「你是本项目的编码工程师。请先认领团队任务 #2（sdk_autoretry），然后开始工作。
>
> **硬约束：运行时零依赖**（只用 node:* 内置模块与内置 fetch），不新增任何 devDependency。
> 对接方案 §10.2 待补能力第一案（你的任务）：客户端 SDK 薄封装：把 `retry_with_backoff` + `retryAfterMs` 变成一行 `autoRetry()`。
>
> **1. 先读源码，后写代码**：归因卡片与响应头的**确切字段名**必须从源码核实（看 `src/loss/` 下归因相关代码与 README §7.2），不要凭 README 措辞猜 JSON 形状。重点核实：
> - `X-Relay-Attribution` 响应头里的内容格式（standard 层）；
> - 错误体 `error.relay_attribution` 的结构（pro 层）；
> - 哪些 `failure_reason` 是可重试的（对应网关 `retryableReasons`）。
>
> **2. API 设计**（薄封装，一个文件搞定）……必须满足『一行调用』目标：用户传 URL/key，SDK 自动在可重试失败上按 `retryAfterMs`（缺省用指数退避+抖动）重试，**不可重试**的失败立即抛出带归因信息的错误。」

**设计要点**：角色声明 → 硬约束前置 → 「先读源码后写代码」（防幻觉）→ 明确 API 形状与默认值来源。结果：一次通过审查（APPROVE），15 项单测全过。

## 证据 B：真机核查类任务书（会话 4 · audit-executor）

> **任务**：逐项执行核查对接方案
>
> 「**严格按照已确认的对接方案，逐项执行核查**：把方案 §3（关键流程）、§5（数据与权限）、§6（计费与结算）、§7（体验设计）中每一条**可运行验证**的条款，在真实进程里跑一遍，记录『方案条款 → 执行命令 → 实际结果 → 判定』。§9 红线中可运行验证的条款也纳入。**只做核查，不做修复。**
>
> **执行方法（必须真实执行，禁止凭文档推断结果）**：
> - 你起的网关实例一律用端口 8790，另一个子代理占用了其它端口。
> - 体验模式可用 `npm run demo`（mock 上游 + 网关 + 看板，单进程，127.0.0.1，管理免令牌）。
> - 需要自定义配置的场景：把临时 YAML 写到 `$env:TEMP` 下（**不要在仓库里新建配置文件**）。」

**设计要点**：「只核查不修复」（职责隔离）、「禁止凭文档推断」（强制真机执行）、端口分工（多智能体并行不打架）、临时文件位置约定（保护仓库干净）。结果：55 条验证，52 过 / 3 不符 / 4 无法验证，全部如实落盘。

## 证据 C：放行裁决类任务书（会话 6 · final-verifier）

> **任务**：最终独立验证与放行裁决
>
> 「你是最终独立验证员，对 api-relay 项目『严格按对接方案执行』的全部交付做放行裁决。
>
> **你的验证清单（独立复核，不轻信前序结论）**：
> 1. 运行 `npm test`，确认 285/285 全过（如有失败，记录详情）
> 2. 确认交付物在盘且非空……」

**设计要点**：「不轻信前序结论」——即使前面 4 个会话都通过了，独立验证员必须自己复跑。这是多智能体互查的关键设计：**任何结论都要能被独立复现**。

## 证据 D：需求类 Prompt（会话 1 · 面板设计）

> 「请启动该项目，并设计一个合理的布局效果：展示整体页面结构与各功能区域的位置安排，说明布局的层次关系与设计依据，确保最终效果清晰、美观且易于使用。」

**设计要点**：需求类 Prompt 短小但要求「说明设计依据」——强迫 AI 给出可辩论的理由而非只交付结果。AI 当轮即产出四步 todo 计划（探索→启动→设计→验证），全程 todo 驱动可追溯。

## 证据 E：批次执行类 Prompt（会话 7 · batch2）

> 「按 docs/tasks/batch2-execution-guide.md 逐步执行」

**设计要点**：一句话启动 6 个连续任务（#6-#11）——因为任务书已把每个任务的前置依赖、验收标准、产出物全部写清（见 `project/docs/tasks/`），Prompt 本身只需一行。**任务书即接口**，这是本项目 Prompt 工程的核心方法论。

## 方法论小结

| Prompt 类型 | 结构模板 | 关键约束位 |
|---|---|---|
| 需求类 | 目标 + 验收维度 | 「说明设计依据」 |
| 代码生成类 | 角色 + 硬约束 + 事实来源 + API 形状 + 禁止事项 | 「先读源码，后写代码」 |
| 核查类 | 条款清单 + 执行方法 + 记录格式 + 职责边界 | 「禁止凭文档推断结果」 |
| 裁决类 | 前序结论（供对照）+ 独立复核清单 | 「不轻信前序结论」 |
| 批次类 | 指向执行指南 | 任务书即接口 |
