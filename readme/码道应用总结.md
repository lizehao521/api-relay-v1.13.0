# 码道在 api-relay 项目开发中的应用总结

> 开发周期：2026-09 ~ 2026-11 ｜ 核心工具：华为云码道（AI Coding，多智能体协作模式）
> 本工作区留存会话：**两轮 48 个**（第一轮 42 + 第二轮 6）｜ 累计交互：**约 5.88 亿 tokens**（588,013,928；第一轮 569,749,124 + 第二轮 18,264,804）｜ 详细证据见 `codearts_proof/`

## 1. 总体方法：多智能体流水线

api-relay 不是「单窗口问答式」用 AI，而是把码道当作**带角色分工的虚拟研发团队**。团队负责人（team-leader）拆解需求为带验收标准的任务书，分派给专职子智能体，形成「实现 → 核查 → 审查 → 放行」四段闭环；设计与调研阶段另设五阶段专家链：

```
                ┌──────────── team-leader（规划/拆解/裁决）────────────┐
                │                                                      │
   任务书驱动    ▼           ▼                ▼                  ▼      ▼
  ┌──────────┐ ┌──────────┐ ┌───────────┐ ┌────────────┐ ┌───────────┐
  │ sdk-     │ │ audit-   │ │ code-     │ │ final-     │ │ web-      │
  │ engineer │ │ executor │ │ reviewer  │ │ verifier   │ │ developer │
  │ 代码生成  │ │ 方案核查  │ │ 代码审查   │ │ 独立放行   │ │ 面板开发   │
  └──────────┘ └──────────┘ └───────────┘ └────────────┘ └───────────┘
   autoRetry    55条验证     APPROVE/      505/505         布局/组件/
   SDK+单测     52过3不符    REQUEST_      独立复跑        端口稳定
                4无法验证    CHANGES       全量测试

  设计与调研五阶段：需求发现 → 设计系统 → 原型构建 → 质量审查 → 导出交付
  平台化四件套（v1.11.0）：多租户/RBAC · 计费账务 · 分布式状态原语 · 协议适配互译层
  配置治理（v1.12.0）：主配置/模型链分离（base + ladders）· 中文档位链名 · build-config 合并校验
  商业化闭环 M0（v1.13.0）：额度池 → 发券 → 领券发 Key → 核销计费 · 6 条管理接口 · 505 测试
```

**每一环都产出落盘文档**（任务书、核查报告、审查结论、交接文档、原型与交付物），可追溯、可复现。

## 3. Prompt 设计质量（我们的做法）

任务书即 Prompt。每份任务书遵循固定结构，确保子智能体一次做对：

1. **角色声明**：你是本项目的编码工程师/核查员/审查员
2. **背景与事实来源**：指明必读文档（README/方案/DECISIONS），禁止凭空推断
3. **硬约束前置**：零运行时依赖、不新增 devDependency、PowerShell 环境、端口约定
4. **验收标准**：可运行验证的条款逐条列出（如「`npm test` 505/505」）
5. **禁止事项**：只核查不修复、不改 package.json、临时文件放 $env:TEMP
6. **产出物定义**：文件路径 + 文档结构 + 需回传的结论格式

示例（SDK 任务书节选，全文见 `codearts_proof/01-Prompt证据存档.md`）：

> 「先读源码，后写代码：归因卡片与响应头的确切字段名必须从源码核实……不要凭 README 措辞猜 JSON 形状。」

**效果**：SDK 任务一次通过审查（APPROVE），15 项单测全过，未返工。

## 4. 工具使用效率

- **上下文管理**：单会话最深达 **7,782 万 tokens**（平台化主控会话，跨 18 小时）；面板/前端主会话达 6,791 万 tokens；42 会话合计 5.70 亿 tokens
- **子智能体并行**：sdk-engineer 与 audit-executor 同时开工（12:50 同时创建），端口分工（8790/8791）避免互相干扰——任务书里显式约定
- **知识沉淀**：每批次结束产出 HANDOVER 交接文档，新会话零上下文冷启动也能接续（batch2 即由新会话按执行指南独立完成；平台四件套由 10-27 主控会话冷启动完成）
- **跨天续作**：多个会话跨日延续（如主控会话 #2 跨 10-19~10-20、#39 跨 10-27~10-28），保证长任务的连续性

## 4.1 第二轮：组合方案上线与排错（2026-11-06 ~ 11-07）

第一轮的 42 个会话完成的是**底座**；第二轮 6 个会话（18,264,804 tokens）完成的是**组合方案的应用层与上线**，性质从"从零生成"转为"**在真实生产环境里定位故障**"：

| 会话 | 角色 | tokens | 关键产出 |
|---|---|---|---|
| `605731b7` | team-leader | 4,548,534 | 主控：拆解 11 个子任务、汇总排错结论、裁决修复方案 |
| `246cc3ac` | team-mate | 306,067 | 端口探测（**结论后被证伪**，作为反例保留） |
| `e1c815e4` | team-mate | 3,445,644 | 只读核查：Key 创建途径、模型可用性（查出 404 隐患） |
| `f3b13c68` | team-mate | 3,685,671 | 部署包修复：CRLF 归一化、重新打包 |
| `05d1331a` | team-mate | 5,757,640 | SSH 重试 → 上传部署 → 公网端到端验收 |
| `1374bbdf` | team-mate | 521,248 | 只读校验：包体积 / 文件数 / CR 字节级复核 |

**这一轮最有价值的不是"做成了什么"，而是四个被自我纠正的错误**（全部写入 `codearts_proof/04`）：

1. 用 Node `net.connect` 探测端口，因 IPv6 回环误判服务未启动（实际监听 IPv4）
2. Windows CRLF 混入 `.env`，key 尾部 `\r` 导致 `KEY_MISMATCH`；而 Git Bash 的 `grep -c $'\r'` 恒为 0，不能作为计量手段
3. 示例配置里的 `qwen3.8-flash-next` 在真实模型清单中不存在，照抄必然 404
4. 白屏时所有资源 `curl` 都是 200，只有真实浏览器渲染才失败——**状态码不能替代渲染验证**

## 6. 结论

码道在本项目中不是辅助工具，而是**研发流程本身的组织形式**：它承担了绝大部分代码生成与文档撰写工作量，同时通过多智能体互查机制保证了质量——最终 **505 项测试全过**（截至 2026-11-03 实跑 505/505）、55 条对接条款逐项核验、审查裁决 APPROVE、平台四件套完成并部署到华为云 ECS 生产实例；后续 M0 商户 token 券闭环亦由码道完成「设计→实现→排错→E2E→线上部署」全链路闭环（新增 21 项测试，40/40 E2E 通过）。这套「任务书驱动 + 四段闭环」的用法可直接复制到其他工程项目。
