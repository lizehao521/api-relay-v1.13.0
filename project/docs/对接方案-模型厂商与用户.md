# 产品对接方案：模型厂商 × 用户（api-relay 双边接入与协同）

> 版本：2026-10-19 ｜ 适用产品：api-relay（OpenAI 兼容多上游聚合网关）  
> 定位：**本方案描述"平台站在中间，左边接模型厂商、右边接用户"这件事怎么落地。**  
> 文中所有机制标注状态：`[已实现]` = 代码已跑通、有测试；`[待补]` = 设计已定、尚未实现；`[可选]` = 按客户需求启用的扩展位。

* * *

## 0\. 一句话概括

> **上游用配置接入、下游用 Key 交付；中间那个进程只做两件事——把成功响应逐字节透传，把失败翻译成用户能直接执行的动作。**  
> 厂商侧我们承诺"不泄露、不改写、可观测"；用户侧我们承诺"同价、可诊断、故障可自愈、花钱可对账"。

* * *

## 1\. 双边结构：两条接入链，一个控制面

```
                        ┌─────────────── api-relay（单进程 / 零运行时依赖）───────────────┐
  模型厂商（上游）        │                                                                  │        用户（下游）
  DeepSeek / 百炼 /      │   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌───────────┐    │   个人开发者 / 企业应用
  硅基流动 / Moonshot /  │   │ 上游池     │→ │ 路由       │→ │ 降损层P2/P3│→ │ 计量 P8    │    │   （OpenAI SDK 直连）
  Zhipu / Ark / Agnes …  │   │ key 池     │   │ 竖/横/闸   │   │ 预检/归因  │   │ 预算闸     │    │   Agent 框架 / 自研
  ─────────────→        │   │ 熔断/半开   │   │ 成本/延迟   │   │ 轨迹 P5    │   │ 三层开关   │    │   ─────────────→
  （HTTPS 出站）          │   └──────────┘   └──────────┘   └──────────┘   └───────────┘    │
                        └──────────────┬───────────────────────────────────────────────────┘
                                       │ 控制面：/admin 看板（8 页签）+ 管理 API（X-Admin-Token）

```

**两条链的对接方式完全不同，不要混：**

|  | 上游链（厂商侧） | 下游链（用户侧） |
| --- | --- | --- |
| 对接手段 | **配置文件 + 环境变量**（`providers[]`） | **签发客户端 Key**（`clients[]`） |
| 变更频率 | 低（接一个厂商就稳定） | 高（每个客户一把 key） |
| 谁操作 | 平台运维 | 平台运营（面板可自助） |
| 出问题时 | 摘除/清熔断/换 key | 轮换/重置额度/禁用 |
| 验收方式 | `relay check` + 真调一次 | `keys/whoami` 粘贴自检 |

## 2\. 对接模式（四种，按业务阶段选）

| 模式 | 适用阶段 | 配置要点 | 用户侧表现 |
| --- | --- | --- | --- |
| **A. 单厂商直连** | 起步（`[已实现]`，推荐） | `starter --vendor <厂> --out starter.yaml`：一个上游、一行 `models`、默认 1 个 key 槽（加 `--env2` 生成双槽 `apiKeys` 数组） | 客户只写厂商原生模型名 |
| **B. 多厂商聚合（横向）** | 单厂商出现稳定性/成本问题后 | 两个 provider **声明同名模型**，`priority` 大者优先；`tags` 标注 `official`/`cheap` | 同一模型名换一家答，`x-relay-model-served` **不变** |
| **C. 档位阶梯（竖向）** | 客户"任务要跑完"诉求出现后 | `modelLadders`：`旗舰: [a-3.0, a-2.5, a-2.0]`；配 `modelCapabilities` 防换错 | 客户写 `"model":"旗舰"`，自动向下推档 |
| **D. 转售套餐（打包出售）** | 有明确付费客户后 | 用 Key 的 `allowedModels` 圈套餐边界 + `quotaCny` 预算 | "拿哪把 key = 买了哪个套餐" |

**组合原则（重要）**：竖向换的是**模型**，横向换的是**供应商**，**跨厂商兜底必须另起名字**（`旗舰-any`）——否则"往下推一档"会偷偷变成"换一家厂"，那是两个不同的决策。

**模式选择决策表：**

| 如果你的痛点是 | 用 |
| --- | --- |
| 只想先跑通、给客户一个统一入口 | A |
| 某厂商经常限流/宕机，客户任务被打断 | B |
| 客户付了旗舰的钱，拿不到旗舰的能力 | C |
| 要按套餐卖、要控制客户花多少 | D + B/C |

## 3\. 关键流程

### 3.1 上游（厂商）接入流程 `[已实现]`

| 步 | 动作 | 命令 / 接口 | 验收标准 |
| --- | --- | --- | --- |
| 1 | 查内置模板 | `node dist/cli.js vendors` | 列出 `deepseek/dashscope/siliconflow/moonshot/zhipu/ark/openrouter/agnes/mock` |
| 2 | 生成起步配置 | `node dist/cli.js starter --vendor deepseek --out starter.yaml` | 单上游单模型，默认 **1 个 key 槽**；加 `--env2 DEEPSEEK_API_KEY_2` 生成双槽 `apiKeys` 数组（`--env2` 为带值参数，值为第二个环境变量名；配置层始终支持 `apiKeys` 多槽） |
| 3 | 填密钥（**不允许明文进文件**） | `export DEEPSEEK_API_KEY=sk-...` + 配置里写 `{ENV:DEEPSEEK_API_KEY}` | `relay check` 通过 |
| 4 | **非标准厂商**配鉴权格式 | `auth: { format: bearerless }`（Agnes 裸 token）/ `api-key-header` / `x-api-key` | 真调 200 而非 401 |
| 5 | 校对模型清单 | `node dist/cli.js pull-models --config x.yaml --dry-run` | 自动排除 video/image；**embedding 保留**（网关实现 `/v1/embeddings` 端点转发，属有意设计）；比对差异 |
| 6 | 声明成本与能力 | `cost: {inputPerMTok, outputPerMTok, cachedInputPerMTok?}` + `modelCapabilities: {tools, contextWindow}` | smart routing 与护栏生效 |
| 7 | 真调验收 | `curl .../v1/chat/completions` | 见到 429→`retry_with_backoff`、余额不足→**402** |

> **两条厂商侧铁律**：① 厂商差异**必须靠配置表达，不能让代码猜**（猜错会静默鉴权失败）；② `/models` 列出 **≠** 你的 key 有权限（实测 Agnes pro 系列在清单里但调用返回 403），拉完必须逐个真调。

### 3.2 用户（客户端）开通流程 `[已实现]`

```
需求确认 → 选层(free/standard/pro) → 圈套餐(allowedModels) → 设额度(token 或 预算¥/quotaCny)
   → 签发 Key（明文只显示一次）→ 交付 → 客户自助核验(keys/whoami) → 计费开始

```

| 环节 | 要点 |
| --- | --- |
| 签发 | 面板「客户 Key → 新建」；服务端只存 **sha256 哈希（带 `relay-key:` 域前缀防彩虹表）**，**明文永不回显**（有测试断言） |
| 交付 | 明文只显示一次，建议落 `chmod 600` 文件；给客户端看**指纹**（`sha256("relay-key:"+key)` 的前 8 位十六进制）作为唯一安全对照物。对拍命令（PowerShell）：`[BitConverter]::ToString([Security.Cryptography.SHA256]::Create().ComputeHash([Text.Encoding]::UTF8.GetBytes("relay-key:"+$key))).Replace('-','').ToLower().Substring(0,8)` |
| 核验 | 客户粘 key 到「粘贴自检」→ 回答四种结论：**有效 / 已禁用 / 已过期 / 不是本网关签发的**（明文不写日志、不落盘、不进台账） |
| 变更 | 轮换（旧 key **立即失效**）/ 禁用 / 重置额度——不可逆动作集中在「更多…」抽屉，后果写在按钮前 |
| 归属 | `tenantId`（租户，用于聚合与对账）+ `label`（展示名） |

### 3.3 单次请求生命周期（用户视角的一跳）

```
auth ──→ precheck ──→ route ──→ upstream ──→ classify ──→ retry ──→ stream ──→ meter
 │          │            │                      │            │                    │
 │          │            │                      │            └ 可恢复错误自动退避重试 │
 │          │            │                      └ raw error → {failure_reason,        │
 │          │            │                        suggested_next.action, recoverable} │
 │          │            └ 竖向换档 / 横向换供应商 / 成本延迟排序                      │
 │          └ 只拦"上游必然拒绝"的；fail-open，唯一例外是危险命令扫描                  │
 └ 客户端 key 比对（常数时间）；未鉴权流量单独成桶 (未鉴权)，不冒充 free               └ P8 落库

```

`[已实现]`，另有 P5 请求级轨迹（`relay trace <traceId>`）可逐步回放。

### 3.4 故障恢复流程（三段式，全自动）

| 段 | 触发 | 行为 | 客户感受 |
| --- | --- | --- | --- |
| 1 | 同一次请求内失败 | 失败上游**当次降权** → 换兜底 → **仍返回 200** | 无感 |
| 2 | 连续失败 ≥ `breakerThreshold`（默认 5） | 熔断该上游 `breakerCooldownMs`（默认 30s），请求直接走兜底 | 无感 |
| 3 | 冷却到期 | **半开试探一次**：成功清零切回主用，失败再熔断 | 原厂修复最长一个冷却周期被发现 |
| 人工 | 上游密钥被吊销 / 长期故障 | 面板「上游 → 摘除」，流量立刻切走；恢复后「恢复」 | 面板可自助，不用登机器 |

### 3.5 计费结算流程

```
请求计量(meter) → 落 SQLite（约 300 B/请求，保留 retentionDays） → 聚合(byModel/byProvider/byFailureReason)
   → 面板「对账 / 账本」页 → 按 tenantId 出账 → 与客户预算(quotaCny)对平 → 超预算返 402

```

`[已实现]`；**多实例时限流与额度是每实例独立的**（`[待补]`：换 Redis Store 才能精确 —— 接口 `incrRate`/`quotaSnapshot` 已隔离）。

## 5\. 数据与权限

### 5.1 凭据体系（三类，绝不混用）

| 凭据 | 存放 | 强度 | 泄露后果 |
| --- | --- | --- | --- |
| 上游 API Key | 配置/环境变量 + 内存；日志经 `redact()` 脱敏；管理接口返回打码 | `{ENV:...}` 插值，**禁止明文入文件** | 烧你的上游额度 |
| 客户端 Key | **只存 sha256**；明文只短暂存在于请求头 | 面板签发、轮换即失效 | 烧该客户额度 |
| 管理令牌 `adminToken` | 环境变量；**常数时间比较** | 建议 ≥ 24 字符随机（`openssl rand -hex 24`） | 全量控制面暴露 |

### 5.2 数据落库与不落库（红线）

-   **不落请求/响应正文**（`[已实现]`，红线 6）；
-   落：度量计数与分布、失败归因、轨迹（含**错误摘要**，需在用户协议中告知）、事件流 `relay_event`；
-   可删：`Store.prune(retentionDays)`（默认 30 天）——**合规删除能力已在**；
-   `meter.hashPayloads` 支持关闭（省 CPU），但关了就没有重复检测；多实例必须配同一个 `RELAY_HASH_SALT`，否则指纹不可比。

### 5.3 权限矩阵（角色 × 操作）

| 操作 | 未鉴权 | 客户端 Key | 运营 | 运维 | 超管（adminToken） |
| --- | --- | --- | --- | --- | --- |
| `/v1/chat/completions` | ❌ 401 | ✅（受层/白名单/额度约束） | — | — | — |
| `GET /admin`（外壳） | ✅ **免鉴权** | ✅ | ✅ | ✅ | ✅ |
| `GET /admin/api/panel-info` | ✅ **免鉴权** | ✅ | ✅ | ✅ | ✅ |
| 其余 `/admin/api/*` | ❌ 401 | ❌ | 读为主 | 读写 | ✅ |
| 签发/轮换 Key、改额度 | ❌ | ❌ | ✅ | ✅ | ✅ |
| 摘除上游 / 清熔断 / 关降损 | ❌ | ❌ | ❌ | ✅ | ✅ |

> **为什么外壳免鉴权（ADR-017）**：浏览器顶层导航带不了 `X-Admin-Token`，而登录门就在那张 HTML 里；外壳一旦也鉴权，配了 `adminToken` 的网关在浏览器里就永远是一页 401 JSON，面板等于不存在。外壳是**纯静态、不含任何数据**的；要连外壳都藏，请用前置反代。**未配置 `adminToken` 时管理接口仅接受 127.0.0.1。**

### 5.4 网络与可达性（对接的隐形前提）

-   **面板能生成 key，但"外网可达"是部署的事**——key 解决"你是谁"，可达性解决"能不能连上"，两者都要有。
-   生产必须：**TLS**（客户端 key 走 `Authorization` 头，明文 HTTP = 公开发布）+ **设 `adminToken`** + **别开 `publicQuotaRemote`**。
-   监听地址用 `::`（双栈）；对外入口推荐**出站隧道**（Tailscale Funnel 主 / cloudflared 兜底），绕过 NAT 与安全组。
-   反代必须 `proxy_buffering off`，否则 SSE 被攒成一坨。

## 6\. 计费与结算

### 6.1 三层计费（代码已实现）

| 层 | 计费 | 降损 | rpm | 并发 | 周期额度 |
| --- | --- | --- | --- | --- | --- |
| free | 无 | **全关**（纯转发） | 20 | 4 | 200K token |
| standard | 按 token | 预检 observe + 归因 header | 300 | 32 | 无限 |
| pro | 订阅 | 预检 enforce + 归因 full + smart routing | 1200 | 128 | 5M token |

-   额度用尽返回 **402（而非 429）**——避免客户端把"没钱了"当"被限流"而无效重试；
-   **402 有两个来源，归因会区分**：网关侧额度（`quotaOverride`/`quotaCny`，`upstream: relay`）与上游侧余额不足（402 直通，`upstream: <厂商id>`）——两者 `failure_reason` 同为 `quota_exhausted`、动作同为 `top_up_balance`，但排查方向不同（前者找平台运营，后者找厂商充值）；
-   `X-Relay-Mode` 响应头**始终回显**本次请求被哪一层、哪套开关处理——"透明"的实现；
-   free 层是**纯管道**：错误体一个字节都不加，守住"同价"承诺与信任假设。

### 6.2 三根轴 + 一条闸（一个"可卖套餐"的组成）

| 轴/闸 | 解决什么故障 | 配置 |
| --- | --- | --- |
| **竖向**（档位阶梯） | 这个模型挂了 → 换同厂另一档 | `modelLadders` |
| **横向**（同模型多供应商） | 这家供应商挂了 → 同名模型换另一家 | 两 provider 声明同名模型，`priority` 大者优先 |
| **闸**（预算） | 客户花超了 → 这个 key 结束 | key 上 `quotaCny`，花完返 402，面板显示「已用完」 |

### 6.3 上游成本与下游定价（对得平才敢卖）

-   上游成本来自 `providers[].cost`（**人民币元/百万 token**，分输入/输出/缓存命中）——**未配置则成本优化退化为优先级路由**；
-   下游计价与上游成本必须在**同一口径**上可对平：**钱按钱算**——用 token 额度冒充预算只能猜（输入 ¥3/M、输出 ¥6/M 时，同样 ¥10 折成 token 数完全取决于输入输出比例）；
-   **额度有两个口径、各自独立判断**：`额度(token)` = "给多少量"；`预算(元)/quotaCny` = "给多少预算"。两者都落库，重启后仍在。

### 6.4 定价纪律（对外话术红线）

-   **不得宣称"降损省 40%"** —— 自家调研（`docs/research/03`）已判定该数字**高估**；
-   正确姿势：先用真实上游跑 **2~4 周**，把 P8 基线（失败分布、重复请求、p95）跑出来，**再定 Pro 定价**；
-   Pro 卖的是\*\*"可观测与可诊断"**，降损是**可选模块\*\*——企业客户默认可关（否则过不了采购与合规）。

### 6.5 单位经济（给财务的最小模型）

```
单客户毛利 = Σ(下游计价 × 用量) − Σ(上游成本 × 用量) − 网关自身开销
网关自身开销 = 归因/预检耗时占比 × 计算成本  → 目标 < 千分之一（P8 直接可读）

```

## 7\. 体验设计（双边各一套承诺）

### 7.1 对用户的四条承诺（可验证）

| 承诺 | 实现 | 客户如何自证 |
| --- | --- | --- |
| **同价**：free 层错误体零附加 | 分层降级表（off/header/full） | `X-Relay-Mode` + 对比错误体 |
| **不改数据**：成功响应零改写 | 红线 1；只允许加白名单响应头 | `x-relay-verify-nonce` → `x-relay-content-hmac` 对拍 |
| **可诊断**：错误翻译成动作 | P3：15 类 `failure_reason` × 11 个 `quick_action`；退避给**具体毫秒** | 看 `error.relay_attribution` 或响应头 |
| **换了模型一定告知** | 四个响应头全称：`x-relay-model-requested` / `x-relay-model-served` / `x-relay-ladder` / `x-relay-switched`（后两个头**无** `model-` 中缀） | 4 个响应头 |

**关键区分（决定客户下一步动作对不对）：**

-   `429 + 余额不足` → `quota_exhausted` + `top_up_balance`（**不可重试**）；余额不足返回 **402**；
-   `404 model_not_found`（改名字的事，附拼写建议）vs `403 model_not_allowed`（去开通的事）——**混着说会把人引向完全错误的方向**；
-   客户端 key 不对（网关自己回 401）vs 上游拒绝密钥（运维换上游密钥）——**两条不同横幅，不同修复动作**。

### 7.2 对厂商的三条承诺

-   **不泄露身份**：不透传上游 `baseUrl`/密钥，只透传白名单响应头；
-   **不改写原文**：`message`/`code` 以上游为准，归因只作**附加**字段/响应头；
-   **可观测**：多 key 池轮换分摊限流，被拒 key 自动报废或短冷却，**对上游表现为正常流量**；上游健康度（熔断、key 可用数、可达性）在面板可视化。

### 7.3 异常体验的兜底

-   **误拦逃生舱**：客户端加 `X-Relay-Precheck: off` 即绕过拦截（照常放行并留痕）——用户不该被治理层的误判锁死；
-   **fail-open**：预检异常/超预算（默认 3ms）一律放行并如实记 `precheckDegraded`；**唯一例外是危险命令扫描**（分界线是**失效后果**，不是性能）。

## 8\. 运营策略

### 8.1 冷启动顺序（不要一上来就面对选项森林）

```
单厂商单模型（模式A）→ 跑通 → 打开 meter 建 P8 基线 → 看清自己的真实失败率与成本结构 → 再加第二个上游（模式B/C）

```

### 8.2 灰度上线五步（推荐顺序）

1.  `storage.driver=sqlite`，三层全 `attribution=off`，先当**纯转发**跑通业务；
2.  开 `meter`，观察 **1~2 周**，建 P8 基线；
3.  `standard` 开 `attribution=header` + `precheck=observe`（只记不拦），观察误拦率；
4.  误拦率 **< 1%** 后，`pro` 开 `precheck=enforce` + `attribution=full`；
5.  有真实收益数据后，再评估 `smartRouting`。

### 8.3 供应商策略

-   **不押单一厂商**：主用 + 兜底必须是**同名模型**（切换期间语义一致，才不会静默换掉客户要的东西）；
-   对**非标准厂商**（Agnes 裸 token 等）差异写进配置、写进模板；
-   **上游超时必须显式设**：对外配置建议 `upstreamTtfbTimeoutMs: 90000` + `upstreamTimeoutMs: 300000`——默认 120s/600s 对阶梯太长，上游一卡请求就一直吊着，阶梯根本没机会往下走。

### 8.4 运营指标（都来自 P8，直接指向行动）

| 指标 | 阈值 / 行动 |
| --- | --- |
| 归因投递率 | < 80% → 该补归因规则了 |
| 自动恢复数 | 越高 = 用户越少人工介入 = 留存价值 |
| 无效重试数（60s 同 payload） | 高 → 引导加幂等键或同轮去重 |
| 预检降级放行数 | **应恒为 0**；不为 0 = bug 信号 |
| 降损层开销占比 | **不应超过千分之一** |
| prompt cache 命中 token | 唯一"不改内容就降本"的路径 |

### 8.5 事件与审计

-   面板**每次写操作落 `relay_event` 表** → 事后审计不需要额外日志系统；
-   被拒的 key 记入台账（**只记指纹/提交形态/长度，永不记明文**）；
-   服务端日志落 `auth.rejected`（含指纹），同类刷屏按 100 次折一条。

## 9\. 注意事项与红线（违反即事故）

| # | 红线 | 原因 |
| --- | --- | --- |
| 1 | **不 fork NewAPI** | 其为 AGPL-3.0 + Section 7，**闭源商用路径被否决**；OneAPI（MIT）错误语义全丢、无降损插槽 |
| 2 | **上游密钥禁止明文入文件** | 一律 `{ENV:NAME}` 插值 |
| 3 | **客户端 key 只存 sha256** | 明文只显示一次，接口永不回显 |
| 4 | **不落请求/响应正文** | 合规与信任；轨迹含错误摘要需在协议中告知 |
| 5 | **不做服务端内容审查** | 避免"我审你内容"的信任与合规问题；免费层靠限速+白名单控滥用 |
| 6 | **一个部署用一个 `storage.path`** | `[已实现]` 换配置 = 换钥匙串，否则同机也不认 key（表现为 401 `invalid_key`） |
| 7 | **对外必须 TLS + `adminToken`** | key 走 `Authorization` 头 |
| 8 | **不为"证明更强"片面宣传** | "错误类型化"是入场券（OpenRouter 已定标准），唯一空白是"**错误可执行化**"；禁语：业内无人做 / 最大 / 覆盖最全 / 省 40% |
| 9 | **不替用户编排/不做 Agent 平台** | 中转站只看得到单请求；越过就不是中转站了 |
| 10 | **不缓存响应** | 命中即零 token 零收入，且非确定性下返回陈旧结果是信任灾难 |
