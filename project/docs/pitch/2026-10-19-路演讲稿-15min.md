## ② 问题：损耗在错误路径（1:00–3:00）

【口播】

> 我们做产品前，先回到第一性原理。
> 
> 一个 Agent，本质是**模型和环境之间的一个传话层**。而一个中转站，是**客户端和上游之间的一个传话层**。两条推论，决定了我们所有的取合：
> 
> 第一，**传话层最大的损耗，不在成功路径，在错误路径**。成功路径做得越少越好——逐字节转发就是最优解；错误路径做得越多越好——把"为什么失败、下一步该做什么"翻译成机器能执行的动作。
> 
> 第二，**传话层的信任，来自"我没有动你的数据"**。任何对成功响应的加工，都是在削弱这个信任。信任一旦破了，价格再便宜也救不回来。
> 
> 所以我们的产品原则只有两句话：**成功响应，逐字节透传，一个字节都不碰；错误响应，翻成可执行的动作。**
> 
> 这不是一个"更好的中转站"，这是一个**对失败负责**的中转站。

【备注】这一段是给技术决策者的"信任锚"：先讲你不做什么，再讲你做什么。第一性原理原文见 `docs/DESIGN.md` §0。

## ③ 定位：是什么，以及刻意不是什么（3:00–5:30）

【口播】

> 先说它是什么。一句话：**一个 OpenAI 兼容的多上游聚合网关**。客户端把 base\_url 指过来，**不改一行业务代码**就能用。
> 
> 它做多上游聚合、多 key 池、熔断与自动故障转移、分层计费。但它最核心的东西，是内嵌的"传话层工程降损"——三件事：
> 
> · **P2，调用前预检**：畸形 tool\_calls、非法参数、模型名拼错，在上游之前就拦下来，省一次往返；  
> · **P3，失败归因**：把 raw error 变成 `{失败类型, 可执行动作, 是否可重试}`；  
> · **P8，损耗量化**：把归因投递率、自动恢复数、无效重试数、**降损层自身的开销占比**全部量化出来。
> 
> 但更重要的是——**我们刻意不做什么**。这张表我建议在座的技术负责人重点看：
> 
> -   **不改写成功响应**。唯一例外是模型名回显，因为严格解码器会崩。
> -   **不做响应缓存**。命中就是零收入，而且 LLM 是非确定性的，返回陈旧结果是信任灾难。
> -   **不做跨请求的意图栈**。那需要我们留存你的会话内容。
> -   **不做 Agent 平台**。中转站只看得到单请求，一旦开始"帮你编排"，它就不是中转站了。
> 
> 一个能清楚说出自己边界的团队，才是值得托付的团队。

【备注】"刻意不是"表见 `README.md` §6.2，与 `DESIGN.md` §9。这是本段的核心——**主动放弃是最强的可信度信号**。

### 4.1 先摆事实（\[口播\] 6–7 分钟）

【口播】

> 我知道在座的第一个问题一定是：**"这个赛道不是早就有人做了吗？我们为什么不直接用免费的？"**
> 
> 是的，早就有人做了。这张表是我们调研的结果，每一个数字都有源码或元数据证据，抓取日期是 2026 年 9 月 11 日。
> 
> · **LiteLLM，5.8 万 star，MIT，免费**；  
> · **NewAPI，4.8 万 star，但它已经迁到 AGPL-3.0**，任何带 UI 的修改版，必须保留它的署名和链接；  
> · **OneAPI，3.7 万 star，但它的主分支事实上已经停滞**；  
> · **OpenRouter，闭源商业**，它**定义了这个行业事实上的错误契约标准**。
> 
> 所以我们从来不假装"这个赛道没人做"。相反，我们承认：**这条赛道已经被工程化过了。**
> 
> 但正因为如此，我们才要问一个更锋利的问题：**在这个已经被工程化过的赛道里，还有哪一格是空的？**

### 4.2 对比页（屏幕切到能力矩阵，\[口播\] 7–9 分钟）

【屏幕】能力矩阵（8 竞品 × 8 维度，缩到 5 行 × 4 列的核心切片）：

|  | 错误类型化 | **错误可执行化** | 流式中途失败 | 许可/品牌自主 |
| --- | --- | --- | --- | --- |
| OpenRouter | ✅ 行业标准 `error_type` | ❌ 无"下一步" | ✅ `200+error+finish_reason` | 闭源 |
| LiteLLM | ✅ 31 类异常 + 谁在限流 | ❌ 无（只有机器决策） | ⚠️ | MIT |
| NewAPI | ⚠️ 内部分层，**对外有损** | ❌ | ⚠️ | **AGPL 传染** |
| Cloudflare / Helicone | ⚠️ 各自半格 | ❌ | ❌ | 闭源 / Apache |
| **api-relay** | ✅ 对齐 OpenRouter 口径 | ✅ **唯一** | ✅ 已实现 | ✅ **自研、无传染** |

【口播——这段建议逐字念】

> 这张表我想请大家只看懂一件事。
> 
> 左起第一列，"错误类型化"——**它已经是 2026 年的入场券，不是卖点**。OpenRouter 已经把 `error_type` 词表变成了行业标准，LiteLLM 甚至比它多走了一步，能告诉你"是上游在限流，还是它自己在限流"。我们这一格，是**追平**，不是领先。我今天不会说我们这里比它们强。
> 
> 但是请大家看第二列——"**错误可执行化**"。这一格，**目前是空的**。
> 
> 什么意思？OpenRouter 会告诉你"这次失败是 `rate_limit_exceeded`"，但它**不告诉你下一步该干什么**。LiteLLM 会自己决定"换一个 deployment 重试"，但那是**机器替你做决定**，不是**给你的 Agent 一行可执行的指令**。
> 
> 我们做的，是把它翻译成 Agent 能直接执行的动作。举两个真实的例子：
> 
> 第一个：上游返回 429，但原因是**余额不足**。行业里绝大多数框架会把它当"限流"，然后**疯狂重试**。我们的归因器会把它判成 `quota_exhausted`，给出动作 `top_up_balance`，并且明明白白告诉客户端——**不要重试**。而且我们余额不足返回的是 **402，不是 429**。
> 
> 第二个：上游返回了 **HTTP 200**，但 finish\_reason 是 `content_filter`。这类失败**不走任何 HTTP 错误通道**，是最容易漏的一类。我们**在 200 的成功响应里**照样产出归因，而且**不改写响应体**。
> 
> 所以我们的定位不是"分类错误"——那是入场券。我们的定位是：**在一个所有人都绕不过、但目前没人做的那一格上，我们是唯一一家。**

【备注】

-   对比页**必须**带脚注口径声明（数据日期 + 证据等级 + 未做线上抓包），这是对技术决策者最强的信任信号。
-   每一条竞品结论都可在 QA 现场翻 `docs/research/01` 的 file:line 证据。

## ⑤ 产品实证（9:00–13:30）

### 5.1 一条命令跑起来（\[口播\]，现场或录屏）

【口播】

> 空口无凭。我们现场跑一条命令。它不需要密钥、不需要配置文件、不需要 `npm install`——因为我们**运行时零依赖**，28 个源文件、9,721 行，只用 Node 内置模块。
> 
> 它在**一个进程**里同时起好模拟上游、网关和看板，然后立刻跑五项自检。

【屏幕】`npm run demo` 五项自检输出（原文）：

```
✓ 健康检查                         HTTP 200
✓ 正常请求（Pro 层）                  HTTP 200
✓ P3 失败归因（注入 429）              归因卡片 + 可执行动作 ✓
✓ P2 预检拦截（畸形 tool_calls）       拦截于上游之前 ✓
✓ 免费层纯管道（无归因）                  错误体零附加 ✓

```

【口播】

> 第五项请特别注意——**免费层是纯管道，错误体一个字节都不加**。因为我们承诺过，同价就是同价，你不用我们的降损能力，我们就不碰你的数据。这就是信任。

### 5.2 P3：归因卡片长什么样（\[口播\]，\[可砍\]）

【屏幕】一次真实请求的轨迹（`README.md` §7.4 原文）：

```
+   180ms FAIL upstream_response HTTP 429
+   181ms FAIL classify          rate_limited → retry_with_backoff
+   182ms ok   retry             第 2 次尝试将在 20ms 后发起

```

【口播】

> 这就是"可执行化"的样子。`retry_with_backoff` 是一个**有限枚举里的动作**，客户端可以把它直接翻译成一行代码。如果有重试时间，我们会给出**具体的毫秒数**，不让客户端去猜。
> 
> 我们对外承诺的反面例子是：**"请检查你的请求"——这不是动作，是废话**。我们有 15 类失败原因 × 11 个可执行动作，每一个动作对应客户端明确该做什么。

### 5.3 P2：只拦"上游必然拒绝的"（\[口播\]，\[可砍\]）

【口播】

> 预检只做一件事：**拦下"上游必然拒绝"的请求**。
> 
> 比如 `tool_calls` 里的 arguments 不是一个合法的 JSON 字符串——这是**最高频的 Agent 框架 bug**。我们把它在上游之前拦下，省一次往返、省一次计费。
> 
> 但我们有三条铁律：**第一，fail-open**——预检自己出错或超预算，一律放行，绝不拖慢主流程；**第二，只拦协议级硬边界**——`temperature` 各上游上限不同，用一套边界拦所有上游就是自我 DDoS；**第三，有误拦的逃生舱**——客户端加一个头就能绕过。
> 
> 唯一的例外是危险命令扫描。为什么它例外？因为**漏拦危险命令会删掉用户的机器，漏拦一个参数只是少一次提前提示**。分界线是失效的后果，不是性能。

### 5.4 P8：把治理层自己的开销摆上桌（\[口播\]，\[可砍\]）

【口播】

> 这是我最想让在座的各位记住的一张表。我们度量**降损层自己**：
> 
> · **归因投递率**：低于 80%，说明有失败模式没被覆盖，该补规则了；  
> · **自动恢复数**：重试后成功 = 用户少一次人工介入；  
> · **无效重试数**：60 秒窗口内重复的 payload；  
> · **预检降级放行数**：**应该恒为 0**，不为 0 就是我们治理层在 fail-open，是 bug 信号；  
> · **降损层开销占比**：预检加归因的耗时除以总耗时——**我们认为治理层不该超过千分之一**；  
> · **prompt cache 命中 token**：这是**唯一"不改内容就能降本"的路径**。
> 
> 记住了吗？**没有度量，就没有下一步优化。** 我们不卖"省了 40%"这种数字，我们卖的是**你能自己看的那张表**。

【备注】"降损省 40% 上游"是自家调研判定为**高估**的数字，已从对外话术删除（`RESEARCH-SUMMARY.md` §4.2）——**现场绝不能提这个数**。

## ⑥ 护城河：主动暴露脆弱点（13:30–15:30）

【口播】

> 到这里，投资人心里一定有一个尖锐的问题：**"你说的这个可执行化，OpenRouter 和 LiteLLM 几周就能抄，那你的护城河是什么？"**
> 
> 我不回避。**这个功能，确实可以被抄。**
> 
> 但护城河从来不是那个功能，是三件更难抄的东西：
> 
> 第一，**归因规则库的数据飞轮**。可执行化的质量，取决于你对真实上游错误的覆盖率——六种错误体形态、火山方舟的未知口径……每一条规则都是拿真实失败换来的。抄走规则容易，抄走"持续发现新失败模式"的能力难。
> 
> 第二，**与 Agent 框架的集成深度**。当客户的 `retry` 策略开始依赖我们的 `quick_action`，迁移成本就不再是"换个 base\_url"。
> 
> 第三，**可私有化部署 + 零运行时依赖**。对合规敏感的企业客户，AGPL 的 NewAPI 用不了，闭源的 OpenRouter 和 Cloudflare 也不能自建——**我们是唯一一个既能自建、又不带许可传染的选择**。
> 
> 我必须诚实地说：**这是我们目前唯一未验证的产品假设——归因卡片，到底能不能提升 Agent 的任务完成率。** 这正是我们最想拿资源去验证的事。

## ⑦ 商业模型（15:30–17:00，\[可砍\]）

【口播】

> 商业模式在代码里已经实现了，不是 PPT。
> 
> 三层：**free** 是纯管道、降损全关；**standard** 是归因进响应头；**pro** 是预检 enforce 加完整归因卡片。
> 
> 一个可卖的套餐，是"三轴一闸"：**竖向**换模型档位、**横向**换同模型的另一家供应商、**闸**是预算——花超了返回 402，明确不让你重试。
> 
> 恢复是自动的、三段式的：同一次请求内换兜底，连续失败到阈值就熔断，冷却到期半开试探一次。**客户全程拿到 200。**
> 
> 需要强调的是：**pro 层我们卖的是"可观测与可诊断"，降损是可选模块。** 因为企业客户默认会关掉它——采购和合规阻力太大。把一个卖不动的东西强塞给客户，是产品经理的失职。

## 附 A：QA 预答（不计入时长，每答 ≤ 30 秒）

| **为什么不用免费的 LiteLLM？** | 三个原因：① 它是 Python，我们是零依赖 Node，私有化部署的运维成本差一个量级；② 它只给你"是机器决定换 deployment"，不给你"给 Agent 看的可执行动作"；③ 品牌和错误契约是它的，你只是在它的产品上加了层壳。 |

| **护城河能持续多久？** | 功能会被人抄，所以护城河在数据飞轮和集成深度。我们主动承认这一点——**这是我们要拿资源去建的东西**。 |
| **你们的错误归因，业内真的没人做吗？** | **"错误的分类"有人做，而且 OpenRouter 已定标准**。空的是"错误的**可执行化**"，以及覆盖 200-with-error 这条最容易漏的路径。（可当场翻 `docs/research/01` §B.4 证据） |
| **为什么不做 Agent 平台 / 响应缓存？** | 因为我们承诺"我只是管道"。做缓存，命中就是零收入，而且 LLM 非确定性下返回陈旧结果是信任灾难；做 Agent 平台，就超出了单请求的可见范围。 |

## 附 B：Demo 备份方案（必做）
