### 页 3 · 第一性原理
**屏幕**：
- Agent = 模型 ↔ 环境之间的**传话层**；中转站 = 客户端 ↔ 上游之间的**传话层**。
- 推论 1：**损耗在错误路径，不在成功路径**（成功路径越少越好，错误路径越多越好）。
- 推论 2：**信任来自"我没有动你的数据"**。

**要点**：产品原则 = 成功响应零改写 + 错误响应可执行化。
**来源**：`docs/DESIGN.md` §0。

---

### 页 4 · 是什么 / 刻意不是什么
**左（是）**：OpenAI 兼容网关（`/v1/chat/completions` 流式、embeddings、completions、models）｜ 多上游聚合 ｜ 多 key 池 ｜ 分层计费 ｜ **降损层 P2/P3/P8** ｜ 内嵌看板
**右（刻意不是）**：
- ❌ 不改写成功响应　❌ 不做响应缓存　❌ 不做跨请求意图栈
- ❌ 不做 Agent 平台　❌ 不 fork NewAPI（AGPL）
**要点**：**能说出边界的团队才可信**。
**来源**：`README.md` §6.2、`DESIGN.md` §9。

---

### 页 5 · 产品三件套
| | 做什么 | 一句话价值 |
|---|---|---|
| **P2 预检** | 上游之前拦下"必然被拒"的请求 | 省一次往返与计费 |
| **P3 归因** | raw error → `{failure_reason, suggested_next.action, recoverable}` | Agent 直接知道下一步做什么 |
| **P8 量化** | 归因投递率 / 自动恢复 / 无效重试 / **治理层自身开销** | 没有度量就没有优化 |

**要点**：P8 是第一优先级——**先把基线量出来，再谈降损**。

### 页 7 · P3 实证：可执行化长什么样
**屏幕**（真实请求轨迹）：
```
+ 180ms FAIL upstream_response HTTP 429
+ 181ms FAIL classify          rate_limited → retry_with_backoff
+ 182ms ok   retry             第 2 次尝试将在 20ms 后发起
```
**要点**：
- 15 类 `failure_reason` × 11 个 `quick_action`；可退避场景给**具体毫秒**。
- **反面例子明令禁止**：`"请检查你的请求"` 不是动作，是废话。
- 关键区分：`429 + 余额不足` → `quota_exhausted` + `top_up_balance`（**不可重试**）；余额不足返回 **402 而非 429**。
- **HTTP 200 里的 `finish_reason=content_filter` 也归因**——最容易漏的一类。
**来源**：`DESIGN.md` 红线 5、`README.md` §7.2。

---

### 页 8 · P2 实证：只拦"上游必然拒绝的"
**屏幕**：可检清单（`tool_calls[].function.arguments` 非 JSON 字符串 = 最高频 Agent 框架 bug）｜ 三条铁律（fail-open / 只拦协议级硬边界 / `X-Relay-Precheck: off` 逃生舱）
**要点**：唯一例外是**危险命令扫描**——分界线是**失效后果**（漏拦会删用户机器），不是性能。
**来源**：`README.md` §7.1、`DECISIONS.md` ADR-014。

---

### 页 9 · P8 实证：把治理层自己的开销摆上桌
| 指标 | 为什么它决定下一步 |
|---|---|
| 归因投递率 | <80% → 该补规则了 |
| 自动恢复数 | 重试后成功 = 用户少一次人工介入 |
| 无效重试数（60s 同 payload） | 高 → 引导加幂等键 |
| 预检降级放行数 | **应恒为 0**，不为 0 = bug 信号 |
| **降损层开销占比** | **治理层不该超过千分之一** |
| prompt cache 命中 token | **唯一"不改内容就降本"的路径** |
**要点**：**我们不卖"省了 40%"，我们卖你能自己看的这张表。**（"省 40%"是自家调研判定为高估的数字，已从对外话术中删除。）

### 页 13 · ★ 唯一空白（本场最重要的一页）
**屏幕**：只放两列——「错误类型化」（多家 ✅）与「错误可执行化」（**全场 ❌，仅 api-relay ✅**）
**逐字话术**（照念，见讲稿 §4.2）：
> 第一列"错误类型化"，它已经是 2026 年的**入场券，不是卖点**——OpenRouter 已定标准，LiteLLM 甚至多回答一步"是谁在限流"。这一格我们**只是追平**。
> 第二列"错误可执行化"——**目前是空的**。OpenRouter 告诉你"这是 `rate_limit_exceeded`"，但**不告诉你下一步干什么**；LiteLLM 是**机器替你决定**，不是**给你的 Agent 一行可执行指令**。
> 我们做的，就是把它翻译成 Agent 能直接执行的动作。
> 我们不是"分类错误"——那是入场券。我们是：**在一个所有人都绕不过、但目前没人做的那一格上，唯一的一家。**

### 页 14 · 护城河（主动暴露脆弱点）
**屏幕**：先放问题——"这个功能，OpenRouter 和 LiteLLM 几周就能抄，你的护城河是什么？"
**答案（三件事）**：
1. **归因规则库的数据飞轮**（可执行化的质量取决于真实失败的覆盖率）
2. **与 Agent 框架的集成深度**（客户的 retry 策略依赖你的 `quick_action`）
3. **可私有化部署 + 零运行时依赖**（AGPL 的 NewAPI 不可商用、闭源托管不可自建——**我们是唯一两者都不是的选择**）
**要点**：主动说"这个功能可以被抄"，比被问出来强十倍。

### 页 15 · 为什么是现在（外部时钟）
1. **2026-03 LiteLLM 供应链攻击**（据报外泄 1TB 源码 / 3TB 客户数据 / 下游密钥）→ 自建网关风险被实证，需求转向"**可信可控层**"。`[E4]`
2. **中国开源模型占 OpenRouter 用量 50%+**（2026-08），单 token 货币化降 ~60% → **成本优化成为主旋律**。`[E4]`
3. **路由成为标准基础设施**：Vercel（2025-08）、Merge（2026-04）、Cursor / Databricks / Ramp / Kong 均入场；Helicone 于 2026-03 被 Mintlify 收购。`[E4]`
4. **资本已给赛道定价**：OpenRouter $113M Series B @ **$1.3B**（≈26x forward revenue）；传闻 Stripe 洽谈以 **~$10B** 收购。`[E4]`（传闻须标注）

### 页 16 · 市场与赛道定位
**生命周期定位**：LLM Gateway 处于「**期望膨胀期后段 → 幻灭低谷**」过渡区；「错误可执行化」仍在「**创新触发期**」。
> 关键判据（报告原文）：**"Revenue grows more slowly than tokens because vendors give core features away, bundle gateways into API management tiers and compete with open-source software."** → 典型幻灭低谷特征。`[E4]`
**测算（口径 + 区间，见 `2026-10-19-市场测算.md`）**：

| 层 | 值 | 口径 |
|---|---|---|
| TAM（2026） | **$1.1B**（区间 $0.66B–$2.76B） | 全球 LLM Gateway 软件/治理层收入 |
| SAM | **$7M–$15M/年**（亚太 × 自建偏好 × Agent 密集） | top-down 与 bottom-up 交叉后收敛 |
| SOM（3 年） | **$0.2M–$0.7M ARR**（35–100 家付费客户） | ARPU $6K/年 |
| 叙事 TAM | APAC 治理支出 **$1.48B**（对标 OpenRouter 5% 抽成） | 口径 C |

**要点**：**TAM 不说 $4B/$11B**（那是平台捆绑收入）；正确说法——"千万美元级的细分，但是 OpenRouter 式的 GMV 抽成入口"。

### 页 17 · 商业模型（代码已实现）
**三层**：free（纯管道，降损全关）｜ standard（归因进响应头）｜ pro（预检 enforce + 完整归因卡片 + smart routing）
**三轴一闸**：竖向换模型档位 ｜ 横向换同模型的另一家供应商 ｜ 闸 = 预算（花超返 **402**）
**三段式自动恢复**：同请求内降权换兜底 → 连续失败熔断 → 冷却到期半开试探
**要点**：**Pro 卖"可观测与可诊断"，降损是可选模块**——企业客户默认关掉它，否则过不了采购与合规。
**来源**：`README.md` §9。
