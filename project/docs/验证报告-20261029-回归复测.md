### P1-1（遗留，未修）· `/v1/messages` 在 Anthropic 入站适配关闭时被静默按 OpenAI 语义处理
- **位置**：`src/gateway/server.ts:374-383`。`inbound?.anthropic` 未开启（`config/relay.yaml` 中**不存在** `inboundAdapters`），但 `supported` 数组硬编码包含 `/v1/messages`。
- **本轮证据（两套配置均复现）**：
  - demo：Anthropic 契约请求返回 **200**，响应体为 `{"object":"chat.completion","choices":[…]}`（OpenAI 形状），Anthropic SDK 无法解析；
  - 文件配置：返回 **401**，耗时 **1139ms**，说明**真实出网并消耗上游配额**，而非"适配未开启"的显式拒绝。
  - 对照组：`/v1/models/{m}:generateContent` 正确返回 404 `unknown_endpoint`，两者行为不一致。
- **影响**：① 顶层 `system` 被忽略 → **系统提示静默丢失**（数据可信类）；② `content` 块数组（image/tool_use）未校验即透传；③ 客户端拿 200 + 错形状，故障被推迟到解析层；④ 无谓消耗上游额度。
- **修复（最小改动）**：`supported` 改为按开关动态生成 —— `inbound?.anthropic` 为假时不列入 `/v1/messages`，落到既有 404 分支并在 message 追加 `请设置 server.inboundAdapters.anthropic: true`。
- **验收**：关闭开关时 `POST /v1/messages` → 404 `unknown_endpoint` 且含 `inboundAdapters.anthropic`，**上游调用计数 0**；开启时与既有 anthropic e2e 一致。

### P2-3（遗留，未修）· `verify_admin.mjs` 运行时崩溃
- **证据**：`TypeError: Cannot read properties of undefined (reading 'info')` at `dist/mock/upstream.js:48`（`this.opts.logger.info`）；根因 `MockUpstreamOptions.logger` 为必填而脚本 `new MockUpstream({ port: 0 })` 未传。
- **影响**：自称"e2e 失败根因定位"的脚本自身即失败；`.mjs` 不在 tsc 覆盖内，任何门禁都发现不了。
- **修复**：`MockUpstream` 对缺省 logger 兜底为静默 logger（从根上消除同类崩溃），或补 logger；若已完成历史使命则删除并归档。
- **验收**：脚本 exit 0 并打印 5 项断言结果，或被删除。

### P2-4（遗留，未修）· 凭据级 fatal 熔断对外降级为 503，且给出自相矛盾的可恢复性指引
- **证据（本轮隔离复现）**：`mock-401` 首次返回 401 `auth_invalid / fix_credentials`；**随即**请求健康的 `mock-small` 得到 **503**，归因头 `auth_invalid;next=fix_credentials;retry_after_ms=30000;recoverable=false`，且**无 `Retry-After` 头**。
- **矛盾点**：`recoverable=false` + `fix_credentials`（不可重试）却携带 `retry_after_ms=30000`（暗示等待后重试）；状态码 503（服务端暂时不可用）与 fatal 凭据错误的语义相反。
- **影响**：客户端按 503/`Retry-After` 语义会持续退避重试一个**永不成功**的请求；同时响应体又劝其重试 30 秒后 —— 与 ADR「别让客户端无效重试」原则冲突（上一轮仅在多上游场景观察到，本轮在单上游闭环验证）。
- **修复**：`openBreakers` 根因全为 fatal（`auth_invalid` / `quota_exhausted` / `permission_denied`）时，状态码取 **401 / 402**、**移除 `retry_after_ms`**；仅过载类根因保留 503 + 冷却提示。
- **验收**：单上游 + 上游 401 → 第二次请求 **401** 且无 `retry-after`、无 `retry_after_ms`；上游 429/503 → 仍为 503 + 冷却提示。

### P3-5（新增）· `RELAY_CONFIG` 为空串时给出原始 `EISDIR`，而非可执行错误
- **证据**：`RELAY_CONFIG=''`（PowerShell `$env:RELAY_CONFIG=''` 实际置为空串）→ `配置装载失败: EISDIR: illegal operation on a directory, read`。

- **验收**：`RELAY_CONFIG='' node dist/cli.js serve` → 结构化提示且不出现 `EISDIR`。

## 5. 假设与风险

- **假设 1**：交付机无真实凭据（沿用上一轮事实）；T4 的"成功链路"以 mock 上游验证，真实上游仅验证到 401 与熔断行为。
- **假设 2**：T4 用 `--host 127.0.0.1` 覆盖配置的 `0.0.0.0`，避免把管理面暴露到局域网。
- **假设 3**：`401 → 503` 的复现使用 demo 单上游；多上游时表现为"可用上游数递减直到全熔断"，语义问题同样成立，但**未做多上游实测**。
- **风险 1（高）**：P1-1 若上线，Anthropic 客户端会拿到 200 + 错形状响应，系统提示静默丢失 —— 属数据可信类缺陷，建议优先于性能项修复。
- **风险 2（高）**：P2-4 使凭据类故障对外表现为"503 稍后重试"，会放大无效重试与告警噪音。
- **风险 3（中）**：P1-2 使 smoke 在验收环境默认不可跑，事故回归门形同虚设。
- **风险 4（中）**：`data/relay.db` 已写入验证期噪声记账，若交付截图直接引用会出现 100% 错误率（本轮 `report` 即为 18 请求 / 18 错误）。
