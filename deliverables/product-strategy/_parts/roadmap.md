## §0 规划设定与方法

- **目标**：为「平台化升级」设定一把可复用的排期尺子（RICE 口径 + 依赖规则 + 词汇表），使后续任一次路线图复核都能在同一口径下重算。
- **输入**：三份零件；`design-proto/01-discovery.md`（目标 G1–G7、缺口 N1–N10）；`project/README.md` §6/§9/§11；`project/DECISIONS.md`（ADR-003/011/021/024）。
- **产出物**：RICE 评分口径、Effort 单位定义、排期三原则、范围边界（非目标）。
- **关键决策**：
  1. **RICE 为排序主尺，但不作为唯一排期依据**。技术零件（§6.1）明确指出「首个多实例部署必须阻塞于 REQ-01/02 完成」——这是**硬依赖门**，RICE 分数低也不能推迟到门槛之后。故本路线图采用 **RICE 排序 + 阻塞依赖修正 + 战略安全项（法律/质量红线）** 三合一，显式在 §1.4、§3 说明修正点。
  2. **禁止引入 NewAPI 代码/UI**（竞品分析附录 A1/D 法律级红线：AGPL-3.0 + Section 7）。任何举措若暗示引入，一律驳回。
  3. **不承诺「降损省 40%」**（ADR-003 已证伪；指标方案 §4.3 判定高估 ~10 倍）。凡涉及节省，一律以 WTCS 可对账口径（计数 × 单价 = 金额）表述。
  4. **范围严格对齐既有边界**：不做响应缓存（P6）、不做服务端改写（P1）、不做 Agent 编排、不做物理多租户（技术零件 §1.2 非目标为硬门禁）。
  5. **季度采用 Now/Next/Later 语义**（比承诺精确日期更诚实），三个季度分别锚定 2026Q4 / 2027Q1 / 2027Q2。
- **RICE 口径定义**：

  | 维度 | 取值口径 | 说明 |
  |---|---|---|
  | **Reach** | 相对刻度 1–10 | 未来 12 个月内受该举措影响的**请求占比 / 客户面**（10 = 平台全部请求，5 = 半数客户，1 = 极小面）。**相对刻度，非绝对人数**。 |
  | **Impact** | 3 / 2 / 1 / 0.5 | 对个体用户的影响：3=大规模、2=中等、1=轻度、0.5=极小（RICE 标准原义）。 |
  | **Confidence** | 100% / 80% / 50% | 80% = 有工程证据/成熟路径；50% = 依赖未验证的客户需求或生态采纳意愿。 |
  | **Effort** | 人月（1 人全职 × 22 工作日） | **单维护者口径**（ADR-011 单人体量），含单测与迁移，**不含**联调环境搭建。技术类由 REQ 人日折算；运营/文档/外壳类按交付物规模估。 |

  **RICE Score = (Reach × Impact × Confidence) / Effort**

- **风险与待办**：
  - ① RICE 的 Reach/Impact 含主观判断，且**不确定项（Confidence=50%）一旦被证伪，排序会显著变化**——已在 §1.3 标注「需先验证」的项。
  - ② 本路线图为 v1.0，随 S1 基线实测（指标方案 §4.2）与竞品复核（竞品分析附录 A）持续校准；**任何对外数字须替换 `[示意]` 占位**。

**前 5 项解读（为什么它们排最前）**：

1. **流式 SSE `error` 帧（38.4）** —— 差异化护城河（错误归因/降损，竞品维度 5 分）在流式路径上的**唯一缺口**；补它等于把满分维度的最后一块黑斑擦掉，且单实例即可、零依赖、Effort 最小。
2. **归因契约对外公开（38.4）** —— 把已有的「可执行化」能力**固化为对外契约**（采纳 OpenRouter `error_type` 词表，不自创），是竞品集体留白、一旦被 Agent 生态采纳即形成锁定的点；主要为文档与测试成本。
3. **成本路由自动化（36.0）** —— 消除「未配 `cost` 静默退化」这一**不可见错误**，Reach 极高（所有成本路由请求）、Effort 极低，是「能卖」可解释性的最低成本改善。
4. **套餐目录（22.4）** —— 让「降损分层（free 纯管道 / standard 归因 header / pro 完整卡片）」变成**可售卖的可见卖点**，是分层变现与自助闭环的入口。
5. **多租户强隔离 & 用量账单（21.6，并列）** —— 拖累分最大的两块（机会损失 24/20）。它们是 WO 策略（用机会补劣势）的落点：**降损窄点再锋利，若没有「客户能自助拿到 key、查用量、看账单、做自检」的外壳，就永远停在工具级**。

> **注意**：RICE 榜的第 8 名「分布式状态外置」虽然分数中游，却是**不可跳过的阻塞门槛**——见下节。

### 1.4 修正：RICE 排序 ≠ 排期顺序（三类修正）

- **目标**：避免「唯 RICE 分数」导致平台化硬伤被无限期推迟。
- **输入**：技术零件 §6.1/§6 范围管理、竞品分析 §5.1 通用红线、指标方案 §4.2 定价依赖。
- **产出物**：三类排期修正规则。
- **关键决策**：

  | # | 修正类型 | 规则 | 具体适用 |
  |:-:|---|---|---|
  | 1 | **阻塞依赖修正（强制前置）** | 技术零件 §6 明确「**首个多实例部署必须阻塞于 REQ-01/02 完成**」。分布式状态外置（RICE 仅 16.0）**必须排在 2027Q1、多副本上线之前**，不得因分数中游而滞后——否则配额/限流语义失真，是收入与信任损失。 | REQ-01/02/09 提到 2027Q1 |
  | 2 | **战略价值修正（不为分数牺牲护城河）** | 归因契约公开与降损验证是**护城河类**，即使部分项当前 RICE 不高（如降损定价验证 7.0），也必须持续推进（跨季），因为它是「差异化可量化」的唯一合法路径。 | 定价路径 S0–S4 跨三季 |
  | 3 | **安全/质量红线修正（不计 RICE 必做）** | 拒绝引入 NewAPI（法律）、清理示意数据与真机验证（信誉）、fail-open 与「成功路径零改写」（信任）属**零容忍红线**，不参与 RICE 排名但一律执行。 | 质量门、横切红线 AC-33~36 |
- **风险与待办**：若 2027Q1 的 Redis 选型 spike（技术零件 Q1）证明自研 RESP 客户端不可行，需升级为主理人裁决项，可能推迟多实例上线并连带推迟 2027Q2 的规模化项。

### 1.5 本部分元信息

- **目标**：产出可重算的 RICE 表与排序，并显式说明排序的局限与修正。
- **产出物**：§1.2 评分表、§1.3 排序榜、§1.4 三类排期修正。
- **关键决策**：用「原始分数 + 理由列」而非只给排序，避免结论被单一权重绑架；每条挂零件编号与缺点编号，保证可追溯。
- **风险与待办**：Confidence=50% 的 4 项（多协议、价格源、SDK、Postgres、降损定价验证）需在触发式启动前先做验证 spike，否则实际 Effort 可能上浮、排序下移。

## §2 季度路线图（2026Q4 / 2027Q1 / 2027Q2）

### 4.1 高管版（战略对齐 · 业务影响 · 关键决策）

> **TL;DR（3–5 行）**
> 1. api-relay 的技术能力已够硬（竞品 15 维对标中「错误归因/降损」是**全场唯一满分**），当前排名第 6，拉低名次的**全是「平台化外壳」**：多租户(2)、SDK(2)、文档站(2)、计费(3)、协议(3)。
> 2. 本次升级的主线只有一句：**先补「能卖」的外壳，再把「错误对 Agent 可执行」做成事实标准**——前者对齐拖累分最大的三块（24/20/16），后者是竞品集体留白、可形成锁定的护城河。
> 3. 三个季度分别是「补齐差异化盲区+亮外壳」→「多实例上线（平台化硬伤 A4）」→「规模化+生态」。
> 4. 定价不做「承诺省 40%」；以**可对账的节省额 WTCS** 为价值证明，Pro 以「额度 + SLA + 可观测」为主锚。
> 5. 需要的帮助：Redis HA 基础设施预算、**2–3 个真实客户样板**用于 4 周对比实验、以及「首个多实例上线」的容忍窗口。

- **战略对齐**：从「工具级自托管网关」→「可对外运营的聚合平台」，路线图直接对齐 01-discovery 的 G1–G7 与缺口 N1–N10；不做响应缓存/Agent 编排（守住「我只是管道」）。
- **业务影响（量化，含口径）**：多租户拖累 24、计费 20、协议 16（竞品 §2.6）；目标为把加权总分从 **326/500（65.2）** 向开源阵营前列推进，硬指标是「客户可自助完成 key→用量→账单→自检闭环」。
- **关键决策点（需高管拍板）**：① 首个多实例上线是否接受为**硬阻塞门**（技术零件 §6）；② Pro 定价是否采纳「可对账节省额作价值证明、非主锚」（指标 §4.4）；③ 是否投入 Anthropic/Gemini 原生适配（**有客户付费验证才启动**）。
- **禁用话术**：不说「业内没人做错误归因」；不引用「省 40%」；不承诺响应缓存/Agent 平台能力。

### 4.2 工程版（技术细节 · 时间线 · 依赖 · 风险缓解）

- **技术骨架**：三个**互不重叠、可独立验收**的改造目标——**G1 状态一致性**（REQ-01/02/09：Redis 外置限流/配额/熔断/key 池）、**G2 协议与流式完备性**（REQ-03 流式 SSE error 帧、REQ-05/06 Anthropic/Gemini）、**G3 平台化运营**（REQ-04 成本路由自动化、REQ-07 多租户强隔离、REQ-08 审计留存）。
- **时间线**：2026Q4 先兑现 G2/G3 低依赖项（T1）；2027Q1 攻 G1 并完成迁移 M0–M2（T2，**多副本上线硬门**）；2027Q2 补 P1/P2（T3）。
- **依赖关系**：REQ-02/09 → REQ-01（共用 Redis）；REQ-06 → REQ-03/05（适配框架）；REQ-07/08 → REQ-10（控制面库）；**首个多实例部署阻塞于 REQ-01/02**。
- **风险缓解（对照技术零件 §5.5）**：R1 Redis 关键路径→fail-open + HA + 连接池；R2 零依赖冲突→**最小 RESP2 自研客户端**、Postgres 归控制面；R3 客户端不接受流中 error 帧→先做兼容实测、分层投递（free=off）；R5 时间窗口径→统一时钟源；R6 迁移重置额度→汇总迁移 + AC-31 门禁 + 迁移前快照。
- **验收纪律**：以技术零件 §5 的 **36 条 AC** 为准，全部以「可对拍测试」验收（复用 ADR-007 mock 上游）；横切红线 **AC-33 success 零改写 / AC-34 fail-open / AC-35 数据面 `dependencies:{}` / AC-36 零回归**。

### 4.3 设计版（UX 目标 · 设计约束 · 可用性考量）

- **UX 目标**：把「客户自助闭环」做成核心体验——**key 申请 → 用量/额度 → 账单对账 → whoami 自检**，让客户不再依赖运营转发（回应 01-discovery 场景 1/5 与缺口 N2）。
- **对账报表体验**：坚持「**计数 × 单价 = 金额**」三段式呈现，而非只给一个「节省 ¥X」；支持 CSV（`CSV_BOM + CRLF`，Excel 直开）供客户自行复算，直接回应「客户能不能自己算出省了多少」。
- **分层可视化**：套餐目录把「free 纯管道 / standard 归因进 header / pro 完整卡片」做成**可见卖点**；`X-Relay-Mode` 回显与权限表达一致。
- **设计约束**：① 零运行时依赖与轻量前端（Preact signals + Vite）；② Anti-Slop 合规、令牌严格消费（沿用 design-proto 设计令牌）；③ **fail-open 必须可见**（预检降级放行数等降级事件要有明示，避免「静默失效」）；④ 多租户隔离须在客户面**处处可见边界**（越权不泄漏存在性）。
- **可用性考量**：错误归因卡需在 **429 限流 vs 402 余额不足**、`finish_reason=content_filter` 的 200 场景、以及**流式 mid-stream 失败**上都有明确、可执行下一步（quick_action），并对齐设计的无障碍与键盘可达要求。

### 4.4 本部分元信息

- **目标**：产出三版定制沟通稿并统一红线话术。
- **产出物**：§4.1–§4.3 三版要点。
- **关键决策**：三版共享事实底座，深度分层（高管 5 行内起步、工程给 REQ/AC、设计给交互与约束）。
- **风险与待办**：对外材料中的数字必须由数据分析师用 P8 实测口径签发后方可发布。
