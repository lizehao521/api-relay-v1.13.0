## 前置声明（口径原则，贯穿全文）

1. **一切金额以"差额"计量，不用绝对值。** 凡称"节省"，必须定义为「实验组相对对照组的成本差额」，否则会把本来就会发生的成本计成收益。
2. **每客户/每结论必须可复算。** 任一对外数字都要给出 `原始计数 × 单价 × 公式`，客户能自己乘出来（见 §5）。
3. **区分"公开假设"（可引用、带来源）与"待验证"（本项目自测前不得对外）。** 全文用 `[公开假设]` / `[待验证]` / `[示意]` 三种标签。`[示意]` 数值一律占位，禁止写入对外话术。
4. **不承诺"省 token"。** 遵循 research/03 §3.2 与 §7.3 的文案纪律：只允许承诺「错误更可读 / 无效往返更少 / prompt 原文不落盘」。降损层通过 P2/P3 主要减少**失败重试**，量级通常为**个位数百分比**；"省 40%"属高估（research/03 附录 C 第 7 条）。
5. **已知边界必须写进分母口径**：多实例部署下无效重试计数、限流、额度是**每实例独立**（README §11），线上跨副本数据会低估，需按 key 分片或落库去重。

## 1. 市场数据支撑：聚合 / 中转 LLM API 市场

### 1.1 元信息

- **目标**：给竞品对标与路线图提供可引用的市场体量、增速与驱动力，并**明确标注**哪些是公开假设、哪些待验证，避免"编造统计"。
- **输入**：公开市场报告（Research and Markets / The Business Research Company / Growth Market Reports / SNS Insider / QY Research / Sacra / Fireworks，见 §7 附录）；本项目 `docs/research/01`。
- **产出物**：§1.2 公开假设台账、§1.3 驱动力、§1.4 不确定性、§1.5 自下而上 TAM/SAM/SOM 模型。
- **关键决策**：**只采信"同一量纲下多家报告交叉"的范围，不取单点峰值**；对 api-relay 的 SOM 用**自下而上**（可验证参数）而非套用行业总额。
- **风险与待办**：① 报告口径差异巨大（见 §1.4），引用须带来源与口径说明；② 国内中转市场无公开权威数据，SOM 参数全部 `[待验证]`。

> **口径警告**：下列报告对"AI Gateway / LLM Gateway / LLM Gateway Platform"的定义**不统一**（是否含硬件、是否含 API 管理模块、是否含 agent/MCP 网关），因此绝对值不可直接相加，只可用于"量级 + 增速"判断。

- **可引用的一致结论（跨报告收敛）**：
  - **增速区间 26%–29%**，且**收入增速显著低于 token 增速**（因核心能力免费化、网关被 API 管理平台捆绑）。
  - 区域：**北美 45%–46% 收入占比**；**亚太增速最快（约 28%–30%）**。
  - 细分结构：**LLM 网关约占企业 AI 网关的 42.8%**；**Agent / MCP 网关是增速最快类型（约 34.8%–36.5% CAGR）**（SNS Insider、Growth Market Reports）。
  - 变现锚点：**按 credits 抽成约 5%**（OpenRouter / Cloudflare）、**SaaS 订阅约 $49/月**（Portkey Production 计划）、**企业版约 $17,500–17,900/年**（Growth Market Reports 估算）。
  - 毛利结构（`[公开假设]`）：AI 网关软件毛利约 **65%–85%**；纯 SaaS 75%–85%，云内嵌/高吞吐托管 60%–75%（MarketPublishers）。
- **token 侧规模（`[公开假设]`，用于反推单价与损耗）**：
  - 全网 LLM API 约 **1.5 千兆 token/月 = 50 万亿 token/日**（Fireworks，2025-11）。
  - 聚合站代表 OpenRouter：**3T+ token/日、8,000,000 开发者、年化收入约 $50M（2026-03）**，周 token 量半年内 **5T→25T**（Sacra / Growth Market Reports）。
  - Portkey：**年化在管 AI 支出 > $1.8 亿、1.2 亿请求/日、24,000+ 组织**（Growth Market Reports）。
  - 需求侧：**77% 的组织把推理视为其主导 AI 活动，平均管理 7 个模型**；**78% 的组织已在至少一个业务职能使用 AI**（typedef.ai，经 R&M 引用）。

### 1.3 驱动力（为什么这个市场会继续长）

1. **受治理流量爆发式增长**：token 量增速远超收入增速，说明"要路由/要封顶/要留痕"的流量池在变大（`[公开假设]`）。
2. **多模型并存成为常态**：组织平均管理 7 个模型 → 需要一个统一控制点，比逐家集成更便宜（`[公开假设]`）。
3. **企业模型支出规模化**：年支出 >$10 万的客户数快速增长（Anthropic 口径一年 7×）→ 成本归因与预算闸成为刚需（`[公开假设]`）。
4. **Agent 带来第二条受治理流**：Agent 自主调工具 → 需要注册与策略；Agent 网关增速最快（`[公开假设]`）。
5. **安全事件推动"可信托管层"集中化**：2026-03 LiteLLM 供应链攻击后被 Mintlify 收购、Palo Alto 以 $1.17 亿收购 Portkey、OpenRouter 拟并入 Stripe —— 市场向"可信、可托管"整合（Sacra / Growth Market Reports，`[公开假设]`）。

### 1.4 不确定性与口径分歧（**必须向路线图/竞品提示**）

| 不确定性 | 证据 | 影响 |
|---|---|---|
| **市场总额口径不一，跨度达 25×** | 2025 年同一"LLM 网关"从 $18.1M（QY 窄口径）到 $3.34B（R&M 宽口径） | 引用绝对值会误导；**只能引用增速与结构** |
| **token 增速 ≫ 收入增速** | 周 token 5T→25T，而市场 CAGR 仅 ~27% | 单 token 变现能力**持续下降**；靠"抽成"难支撑高估值 |
| **捆绑化侵蚀独立网关** | 微软称 Azure API Management 内嵌即网关，而非独立产品 | 独立中转站需靠**差异化（可自托管/零依赖/降损可对账）**而非广度竞争 |
| **国内中转无公开数据** | 竞品调研仅 CloseAI 一家可用（`docs/research/01` §1.8） | 国内 SOM 无法外部引用，**必须自测** |
| **各报告"AI Gateway"是否含 Agent/MCP 不明** | 定义漂移 | 远期总额不可比 |

### 1.5 面向 api-relay 的自下而上 TAM / SAM / SOM（`[待验证]`，含模型与参数）

> 采用**自下而上**，因为 api-relay 是**可自托管的软件 + 分层订阅**，与"市场总盘子"关系弱，与"你的目标客户数 × 钱包"关系强。以下参数**全部为待验证**，S1 期用真实客户数据回填。

**TAM（可服务的聚合/中转需求）**
```
TAM_年 = Σ_i (目标客户 i 的年模型 API 支出) × 中转渗透率
```
- 目标客户 i：以"有 Agent/多模型、且有合规或成本诉求的团队"为口径（`design-proto/01` Q2 默认 B 端为主）。
- 中转渗透率：`[待验证]`（Growth Market Reports 估算全网约 55% 的模型支出"经过网关"，但其中"独立中转站"占比未知）。

**SAM（api-relay 能力覆盖的部分）**
```
SAM = TAM × 技术可达率
技术可达率 = OpenAI 兼容请求占比 × (1 − 需 Anthropic/Gemini 原生协议占比)
```
- `[待验证]`：README §11 已知 Anthropic/Gemini 原生仅留位；覆盖不到的原生协议客户不计入 SAM。

**SOM（12 个月内可获取）**
```
SOM = 可触达客户数 × 单客户年支出 × 可赢率
```
- 可触达客户数：`[待验证]`（由销售渠道与自托管分发决定，**不使用行业总额推导**）。
- 可赢率：`[待验证]`（差异化臂 = 降损可对账 + 可自托管 + 零依赖供应链）。
- **SOM 输出的主锚点是"单客户年支出"，而非市场总额** —— 它同时也是 §4 定价路径的输入。

### 1.6 给竞品与路线图的引用纪律

- 允许引用：**增速区间 26%–29%、亚太最快、Agent 网关增速最快、token 增速 ≫ 收入增速、捆绑化风险、5% credits 抽成 / $49 月订阅锚点、毛利 65%–85%**（均带来源）。
- 禁止引用：任何把不同口径报告**相加**得到的"大盘"数字；任何未标 `[待验证]` 的国内 SOM。

## 2. 「降损价值可对账」指标体系

### 2.1 元信息

- **目标**：把 README §7.3 的定性口径，落成**有定义、有公式、有数据来源、有阈值、有客户/我方双层意义**的指标字典，使"降损到底省了多少"可被客户自行复算。
- **输入**：README §7.1–§7.3、research/03 §3.1（M1–M13）、`providers[].cost`、`quotaCny`、`MeterRecord`、`TraceRecord`。
- **产出物**：§2.2 指标字典（9+2 项）、§2.3 指标→金额映射、§2.4 口径冲突与待办。
- **关键决策**：**新增两项金额/时长指标**（无效 token 成本节省额 ¥、平均修复时长/人工介入次数下降），因为原 P8 指标全是"计数/比率"，无法直接支撑定价；**金额指标一律以"对照差额"定义**。
- **风险与待办**：① 开销占比阈值存在双口径冲突（见 §2.4）；② "人工介入次数"网关侧不可直接观测；③ 无效重试跨副本低估。

### 2.2 指标字典（口径冻结建议）

> 记号：`N` = 周期内进入网关的请求数（`relay.requests.total`）。单价 `p_in/p_out/p_cache` 取自 `providers[].cost.{inputPerMTok, outputPerMTok}`（未配置价格的上游计入 `relay.cost.unknown`，**不得默认 0**）。金额单位为元（¥），成本内部以 micro-CNY 整数累计后还原。

| # | 指标（建议名） | 定义（一句话） | 计算公式 | 数据来源（本项目字段） | 目标阈值 | 对客户的意义 | 对我方的意义 |
|---|---|---|---|---|---|---|---|
| 1 | **归因投递率 ADR** | 失败中被规则成功归因的比例 | `ADR = (Σ relay.attribution.hits − Σ relay.attribution.unclassified) / Σ relay.upstream.errors × 100%` | `relay.attribution.hits`、`relay.attribution.unclassified`（M3）、`relay.upstream.errors`（M2） | ≥80%（README §7.3）；成熟态 ≥95% | 网关是否真把失败讲清楚 | `unclassified` 即**下一个补规则 TODO 清单** |
| 2 | **自动恢复数 ARR_count** | 本层自动重试/换上游后成功的请求数 | `ARR_count = Σ relay.reduction.recovered_requests`（= outcome=success 且 steps 含 retry 的请求） | `TraceRecord.steps`（含 `retry`/`route` 阶段）、`relay.requests.total{outcome=success}`（M4/M12） | 定义清楚；`自动恢复率 = ARR_count / N` | 少一次人工介入 = 少一次业务中断 | 留存价值；"把失败变成功"是最硬收益 |
| 3 | **无效重试数 DR（60s 同 payload）** | 60 秒窗口内同 `(keyId,payloadHash,model)` 第 2 次起的请求数 | `DR = Σ relay.retries.duplicate`，窗口 W=60s | `MeterRecord.duplicateInWindow`（M5） | 越低越好；高 → 引导幂等 | 客户"自己在瞎重试"的浪费 | 该引导客户端加幂等键；**口径声明：单副本内计数，多副本低估** |
| 4 | **预检拦截数 PB** | 因 A 类硬边界在上游之前被拦的请求数 | `PB = Σ relay.precheck.blocked` | `relay.precheck.blocked`（M11） | 越高（且误拦=0）越好 | 每条 = 省一次上游往返 | 每条 = 省一次上游往返 + 若上游对畸形请求计费则其 token（**默认不假设省 token**） |
| 5 | **预检降级放行数 PD** | 预检内部异常/超预算触发 fail-open 放行的次数 | `PD = Σ relay.precheck._degraded`（计数器 `precheckDegraded`） | `precheckDegraded`（README §7.1 铁律 1） | **恒 = 0** | 网关的真实性自证 | **≠0 即 bug 信号**（治理层在静默失效） |
| 6 | **降损层开销占比 OH** | 治理层自耗占总耗时比例 | `OH = Σ relay.overhead.duration / Σ relay.request.duration × 100%`（分阶段 `precheck/classify/fingerprint/meter/trace`） | `relay.overhead.duration`（M10）、`relay.request.duration`（M6） | **对外承诺 ≤0.1%（千分之一，README §7.3）**；工程熔断线 `OH>3%` 或 `precheck p99>2ms` 自动降级（research/03 M10） | "治理层不拖慢主流程"的可证证据 | 超线自动降级为 observe/off |
| 7 | **prompt cache 命中 token CT** | 命中上游 prompt cache 的输入 token 数 | `CT = Σ cached_prompt_tokens`；`命中率 = CT / Σ prompt_tokens`（缺失请求不进分母） | `usage.prompt_tokens_details.cached_tokens`（OpenAI 系）/ `usage.prompt_cache_hit_tokens`（DeepSeek）、`relay.prompt_cache.hit_ratio`（M8） | 命中率越高毛利越好 | **唯一"不改内容就降本"的路径** | 上游成本降、客户按原价付费 → **毛利改善** |
| 8 | **无效 token 成本节省额 WTCS（¥）🆕** | 实验组相对对照组"为无效调用多花的钱"的减少额 | 见 §2.3 拆解式 | `relay.cost.total`（M9，micro-CNY）、`relay.reduction.wasted_tokens`、`providers[].cost` | 点估计 + 95% CI 下界 > 0 | **能自己算出省了多少钱的核心字段** | Pro 溢价的**唯一合法数据依据** |
| 9 | **平均修复时长下降 / 人工介入次数下降 🆕** | 从失败到恢复的时长中位数，及人工介入次数的减少 | `MTTR = median(recover_at − fail_at)`；`介入下降 = 基线组介入数 − 实验组介入数` | `TraceRecord.steps{offsetMs, failedAtStage}``+ 客户端 `X-Relay-Session-Id` 关联 + 外部工单计数 | 无绝对阈值，**方向性**（实验组更低） | 直接对应 SLA 与团队工时 | 留存/续费的定性+半定量证据 |
| 10 | （护栏）`relay_error` 计数 | 治理层自身故障数 | `Σ relay.requests.total{outcome=relay_error}` | M1 | **恒 = 0** | 承诺"非单点故障" | 必须永远为 0 |
| 11 | （护栏）A 类误拦率 | 预检误拦自证数占比 | `误拦率 = 误拦数 / PB` | `relay.precheck.false_positive`（M11） | **A 类 = 0** | 不被治理层误判锁死 | 误拦率超线 → 规则自动降 observe |

> **分母口径纪律**：`N`、`relay.requests.total` 的 `outcome` 必须区分 `success/client_error/upstream_error/relay_error/aborted`（M1）；`aborted`（客户端取消）**单独看，不污染错误率**。

### 2.3 从指标到金额：WTCS 的严格拆解（**避免"把本该花的钱算成省"**）

设对照组（纯管道）为 `C`、实验组（全降损）为 `E`，同一观测窗口、同一客户、同一模型组合。

```
① 失败浪费 token 成本（精确、可对账）
   WastedCost = Σ_{(outcome≠success 且上游已返回 usage)} (prompt_tokens × p_in + completion_tokens × p_out) / 1e6
   来源：relay.reduction.wasted_tokens（M12）+ relay.cost.total（M9）

② 预检避免成本（默认不可对账，须显式声明）
   PrecheckSaved = Σ_{被拦截请求} (若放行本会产生且上游会计费的 token × 单价)
   默认 = 0（多数上游对"协议级畸形请求"不产生计费）；仅在实测确认上游计费时启用该分项

③ 缓存净省（真实但归因于上游能力与用户行为，非我方改写功劳）
   CacheSaved = Σ cached_prompt_tokens × (p_in − p_cache) / 1e6
   来源：M8

④ 无效重试避免成本（近似）
   RetrySaved = (DR_C − DR_E) × 单次请求平均成本

WTCS（节省额，¥） = [WastedCost_C − WastedCost_E]        # 主项：失败浪费下降
                  + [PrecheckSaved_E]                     # 次项：默认 0
                  + [CacheSaved_E − CacheSaved_C]          # 缓存净增量
                  + [RetrySaved]                           # 近似项
```
- **单位与周期**：单客户口径下汇总为 **¥/年**（观测窗口按窗口长度×线性外推，并在报表标注外推因子）。
- **强制披露**：每一条金额旁必须并列 `原始计数 / 单价 / 公式`，允许客户用其后台账单核对（见 §5）。
- **话术边界**：`WastedCost` 只作内部基线与对账，**不进对外 SLA/宣传**（research/03 §3.4 反方 4：避免"把失败做大以显得收益高"的目标错位）。

### 2.4 口径冲突与待办（发现的问题，交路线图/工程）

| 冲突 | 现状 | 建议裁决 |
|---|---|---|

## 3. 实验方案：验证"降损价值可对账"

### 3.1 元信息

- **目标**：设计一套可落地的实验，同时回答两个问题——(a) 降损层是否**统计显著**地减少无效重试/浪费 token；(b) 单客户**年节省额**（¥）是否显著 > 0，足以支撑定价。
- **输入**：§2 指标字典、§1.5 单客户年支出锚点、现有分层（free 纯管道 / standard / pro 全降损）。
- **产出物**：主/辅实验设计、样本量估算、窗口、成功判据、混杂控制与统计方法。
- **关键决策**：**双层设计**——(主) 同层内随机 A/B 做**显著性**（请求量大、快）；(辅) free 纯管道 vs pro 全降损做**前后/分层对比**做**价值核算**（客户少，只做描述 + bootstrap CI，不追求显著）。原因：READM/01-discovery 的 free 与 pro 在 rpm/额度/并发上**天然不同**，直接比较存在严重混杂，不能作为唯一证据。
- **风险与待办**：① 客户数可能不足以做客户级显著性 → 显著性放在请求级；② free 层与 pro 层上游权重/模型白名单可能不同 → 须用协变量调整；③ 观测期若跨发版/大促会污染 → 排除或设哑变量。

### 3.2 实验设计

**实验 A（主，claim 显著性）：同层随机对照 A/B**
- 分组单元：**请求级**；在同一 tier（standard 或 pro）内按 `hash(payloadHash + model)` 稳定 50/50 随机，使**同一客户、同一模型**同时落入两组（客户即自身对照，消除客户异质性）。
- 对照组 C：`X-Relay-Loss-Reduction: off`（纯管道，预检/归因关闭，字节级等价，README §7）。
- 实验组 E：`X-Relay-Loss-Reduction: on`（预检 enforce + 归因 full）。
- 上游与路由：**两组共享同一上游池与同一路由策略**（否则上游波动成为混杂）。
- 优势：分组在请求级随机 → 混杂最小、样本量最大、判定最快。

**实验 B（辅，价值核算）：free 纯管道 vs pro 全降损（前后 + 分层对比）**
- 单元：**客户（cohort）**。
- 设计：对同一批客户做**前后对比（pre/post，ITS）**；并保留一组"自愿停留在 free/standard"的客户作**天然对照（DiD）**。
- 用途：产出**单客户年节省额（¥）**与 §2.3 拆解，作为定价输入；**仅做描述性与 bootstrap CI，不下显著性结论**。
- 混杂声明：free/pro 在 rpm(20/1200)、并发(4/128)、额度(200K/5M)、模型白名单上不同 → 价值核算必须用协变量调整并把"能力差异"与"降损差异"分账。

### 3.3 样本量估算

**方法**：比率类指标用**双比例 z 检验**；金额/分位用**bootstrap** 与秩检验；文档预先声明 α 与 power。

**公式（每组请求数，双比例）**
```
n_per_group = ( z_{1−α/2}·√(2·p̄·(1−p̄)) + z_{1−β}·√(p1(1−p1)+p2(1−p2)) )² / (p1−p2)²
p̄ = (p1+p2)/2
```

**工作示例（α=0.05 双侧，power=0.80，基线 p1=5%）**

| 目标相对降幅 | p2 | 每组请求数 | 合计请求数 |
|---|---|---|---|
| 10% | 4.5% | ≈ 28,400 | ≈ 56,800 |
| **20%（默认主终点）** | **4.0%** | **≈ 6,750** | **≈ 13,500** |
| 30% | 3.5% | ≈ 2,840 | ≈ 5,680 |

- **结论（请求级）**：以"无效重试率/失败率相对下降 20%"为主终点，**每组约 6,750 请求、合计约 1.35 万请求**即可在 80% power 下检出。按 api-relay 单客户日请求量，此量级通常在数天内累积，**样本量不是瓶颈，观测窗口才是**。
- **客户级（价值核算，参考值）**：若强行做两样本均值检验、目标效应 Cohen's d=0.3，需约 **175 客户/组（合计 ~350）**；配对设计约 **88 对**。**`[待验证]` 早期客户数很可能不足** → 因此客户级只用 bootstrap CI 描述（1,000 次重采样，BCa 区间），不签发显著性结论。

### 3.4 观测窗口

- **建议：4 周**（= 1 周**洗牌期** + 3 周**观测期**），覆盖 ≥2 个完整周节律（周中/周末）与发版节奏。
- **最低可接受：2 周**（降级为方向性证据，只报区间不报"达标/未达标"）。
- **理由**：LLM 流量有强烈周节律与账单日效应（月末/月初），窗口 <2 周会引入系统性偏差；洗牌期用于让随机分组、缓存、熔断状态稳定。

### 3.5 成功判据（决策规则，任一护栏不满足即判失败）

| 类别 | 判据 | 阈值 |
|---|---|---|
| **主终点** | 无效重试率（DR/N）相对降幅 | **≥20% 且 p<0.05（双侧）** |
| **次终点** | 自动恢复率、wasted-token 成本/请求、prompt cache 命中率 | 方向为正且 CI 不跨 0 |
| **价值终点** | 单客户年节省额 WTCS | 点估计 ≥ **¥1,000/年**[示意] 且 95% CI 下界 > 0 |
| **护栏-性能** | 降损层开销占比 OH / precheck p99 | OH ≤ **0.1%**；p99 ≤ 2ms |
| **护栏-正确性** | A 类误拦率 / `relay_error` / PD | 误拦 = **0**；relay_error = **0**；PD = **0** |
| **护栏-非劣** | 成功率、p95 总延迟 | 实验组成功率 ≥ 对照 − **0.5pp**；p95 延迟 ≤ 对照 × **1.05** |

### 3.6 混杂变量控制与统计方法

**混杂控制**
1. 随机化单元与分层：请求级稳定哈希；按 `tier / model / 客户规模 / 上游` 分层。
2. 同客户自身对照：同 key 同时进两组，消除客户异质性。
3. 上游与路由固定：两组走同一上游权重，避免上游波动混淆。
4. 时间对齐：两组在同一时间窗口内交替采样（ratio-metric 时间序列法），抵消时变效应。
5. CUPED / 协变量调整：以**洗牌期**的请求量、失败率为协变量，降低方差、提升 power。
6. 排除与哑变量：发版、大促、上游事故窗口排除或设为哑变量。
7. 多实例一致性：按 key 一致性哈希固定分组，防同客户跨组污染；跨副本计数需去重（§2.4）。

**统计方法**
- 比率/计数：双比例 z 检验；或**泊松 / 负二项回归**（带协变量，处理过离散）。
- 金额/分位：**bootstrap（1,000 次）BCa CI** + Mann–Whitney U 稳健检验。
- 前后对比：**ITS（中断时间序列）**；有天然对照时用 **DiD**。
- 多重比较：主终点单一；次终点用 Bonferroni 或 Holm 校正。
- 中途窥视：采用**固定样本显现**或 **O'Brien-Fleming 序贯**，控制 α 膨胀。
- 效应报告：同时给**绝对差**与**相对差** + 95% CI，并预声明最小可检测效应（MDE）。

## 4. 从基线到定价的验证路径（5 个阶段）

### 4.1 元信息

- **目标**：把"价值难量化 / 定价无据"变成一条**可执行、可回退**的验证链：先度量 → 得节省额 → 反推溢价 → 定区间 → 试点验证。
- **输入**：§2 指标字典、§3 实验结论、`quotaCny`/成本路由、公开定价锚点（§1.2）。
- **产出物**：§4.2 五阶段路线表、§4.3 反推公式与示意、§4.4 定价区间建议。
- **关键决策**：**Pro 溢价 = 节省额 × 价值捕获率 − 我方增量成本**；若仅靠"降损"不足以支撑高订阅价，则按 research/03 §7.4 反方 1 把 Pro 重新定位为**"可观测与可诊断"**（失败归因、trace、成本/cache 报表、SLA），降损节省额作**价值证明/续费理由**而非主要定价支柱。
- **风险与待办**：① 捕获率与心理阈值无外部权威，属 `[待验证]`；② 若线路图先做后端改造（多实例），可能推迟基线期；③ 早期客户数少 → 定价初期只能是区间而非点价。

### 4.2 五阶段路线（阶段数 = **5**）

| 阶段 | 名称 | 目标 | 输入 | 输出 | 风险与待办 |
|---|---|---|---|---|---|
| **S0** | 埋点就绪 | 冻结口径、埋点齐备 | §2 指标字典；现有 `relay.*` 计数器、`TraceRecord`、`MeterRecord`、`providers[].cost` | 口径冻结文档 + 埋点自检清单（PD=0、ADR 可算、WTCS 三段可算） | 埋点缺 `cached_tokens` 或 `cost` 未配置 → `relay.cost.unknown` 不为 0；先跑 `relay report` 验证 |
| **S1** | 基线期 | 跑出 2–4 周真实 P8 基线 | 真实上游；实验 A（同层 A/B）+ 实验 B（free vs pro 前后） | 基线报表：失败率、ADR、DR、PB、OH、CT、WTCS、MTTR | 流量不足/窗口过短 → 证据降级；上游事故污染 → 排除窗口 |
| **S2** | 价值量化 | 得单客户年节省额（¥）与拆解 | S1 数据；§2.3 拆解式 | `WTCS(¥/年/客户)` 点估计 + 95% CI；四成分占比（失败浪费/预检/缓存/重试） | 客户数少 → 只报 CI；缓存省归类于上游能力，**不得计入我方"改写功劳"** |
| **S3** | 溢价反推 | 由节省额反推可支撑溢价 | S2 的 WTCS；我方增量成本（降损层 CPU/存储/支持） | 溢价上限与建议值（¥/年、¥/月） | 捕获率无基准（待验证）；须扣除我方成本，避免"虚高溢价" |
| **S4** | 定价区间与试点 | 定区间并小范围验证 | S3 结果；公开锚点（$49/月、5% 抽成）；客户价格访谈 | 定价区间建议 + 试点方案（价格敏感度/续费意图） | 早期只能区间定；须以"可对账节省额 ≥15% 溢价"为可持续门槛 |

### 4.3 反推公式与示意计算（`[示意]`，S1 实测后替换）

```
溢价空间（上限，¥/年） = WTCS(¥/年/客户) × 价值捕获率(CaptureRate)
溢价建议（¥/年）       = WTCS × CaptureRate − 我方增量服务成本/客户
月订阅价（¥/月）        = 溢价建议 / 12
可持续性约束           = 溢价建议 / WTCS ≥ 15%   且   溢价建议 ≤ 客户年 API 支出的 3%–8%   # 心理/可比锚点
```

**示意（占位，禁止对外）**：设客户年 API 支出 ¥50,000

| 分项 | 说明 | 金额[示意] |
|---|---|---|
| 失败浪费 token 成本下降 | 3% 失败率、60% 可恢复、失败调用 token 已计费 | ≈ ¥250 |
| 无效重试避免成本 | 60s 同 payload 重复占比 | ≈ ¥300 |
| 缓存净省 | 命中率提升 × (p_in − p_cache) | ≈ ¥1,500 |
| **WTCS 合计（保守）** | ≈ **年支出的 4.1%** | **≈ ¥2,050/年** |
| × 捕获率 25% | | ≈ ¥510/年 |
| **月溢价建议** | | **≈ ¥42/月** |

> **对比"省 40%"**：按旧话术客户年省 ¥20,000，是本模型（¥2,050）的 **~10 倍** —— 可见 README §11 / research/03 附录 C 判定"40% 是高估"在数量级上成立。**定价必须建立在可对账的 WTCS 上，而非 40%。**

### 4.4 定价区间建议（`[示意]`，随 S2/S3 更新）

| 客户画像 | 年 API 支出[示意] | WTCS(按 4%)[示意] | 建议 Pro 溢价 | 定位 |
|---|---|---|---|---|
| 轻度（低失败率） | ¥10,000 | ≈ ¥400/年 | ¥0–8/月 | 降损价值弱 → 靠"可观测"免费/引流 |
| 中度 | ¥50,000 | ≈ ¥2,050/年 | **¥29–59/月** | 主战场，"可对账节省"覆盖溢价 ≥15% |
| 重度（高失败/高 Agent） | ¥200,000 | ≈ ¥8,000+/年 | **¥99–199/月** | 节省额足以支撑，绑定 SLA + 可观测 |

- **参考锚点**：Portkey 生产版 **$49/月**（≈ ¥350）、OpenRouter/Cloudflare **credits 抽成 5%**（`[公开假设]`）。
- **结论**：**api-relay 的降损节省额通常不足以单独支撑 $49/月 量级**（重客户除外）；因此 Pro 定价应以 **额度 + SLA + 可观测与可诊断** 为主锚，"可对账节省额"作**价值证明与续费依据**（与 research/03 §7.4 反方 1 一致）。

## 5. 指标看板建议：客户可自助对账的报表

### 5.1 元信息

- **目标**：回答"客户能不能自己算出省了多少"——每个字段都可复算，且给出求和式与单价来源。
- **输入**：§2 指标字典、§2.3 WTCS 拆解、`X-Relay-Mode`/trace 可解释机制（research/03 §7.3）。
- **产出物**：客户面只读对账报表字段清单 + 我方面运营/销售视图。
- **关键决策**：**展示"原始计数 × 单价 = 金额"三段式**，而非只给一个"节省 ¥X"；客户可导出 CSV 自行核对（沿用 `CSV_BOM + CRLF`，Excel 直开）。
- **风险与待办**：① 多租户隔离（`tenantId` 过滤）为原型表达、后端待实现（`design-proto/01` N10）；② 单价可能未配置（`relay.cost.unknown`）→ 报表须提示。

### 5.2 客户面「对账报表」应展示字段（可复算）

| 区块 | 字段 | 公式/来源 | 客户能否自算 |
|---|---|---|---|
| 概览 | 周期、请求总数 N、成功率、总消耗(¥) | `relay.requests.total`、`relay.cost.total` | ✅ |
| **降损-失败** | 自动恢复数 ARR_count、恢复价值(¥) | §2.2 #2；× 单次请求平均成本 | ✅ |
| **降损-重试** | 无效重试数 DR(60s 同 payload)、避免浪费(¥) | §2.2 #3；(DR_C−DR_E)×单次成本 | ✅ |
| **降损-预检** | 预检拦截数 PB、避免上游往返数、避免 token 成本(¥，默认 0 并注明) | §2.2 #4、§2.3 ② | ✅（含免责说明） |
| **降损-缓存** | prompt cache 命中 token CT、命中率、缓存净省(¥) | §2.2 #7；`CT×(p_in−p_cache)/1e6` | ✅ |
| **降损-浪费** | 失效 token 成本(¥)、占比 | §2.3 ① | ✅ |
| **稳定性** | 归因投递率 ADR、错误分布 | §2.2 #1 | ✅ |
| **体检** | 降损层开销占比 OH、p99、A 类误拦、relay_error、PD | §2.2 #6/#10/#11/#5 | ✅ |
| **合计** | **本周期可对账节省额 WTCS(¥)** + 四成分占比 | §2.3 | ✅ |
| **明细** | 每模型单价表 `p_in/p_out/p_cache`、外推因子、口径说明 | `providers[].cost` | ✅ |
| **导出** | CSV（含公式列）/ JSON | 沿用现有导出 | ✅ |

### 5.3 客户自算流程（报表内嵌说明书）

1. 打开对账报表 → 看「合计：本周期可对账节省 ¥X」。
2. 点开**四成分明细** → 每项给出 `计数 × 单价 = 金额`，与你的后台账单逐项核对。
3. 下载 CSV → 用报表内的**单价表**重算一遍，应得到同一数字。
4. 若某模型显示"单价未配置"，该部分金额标注为"待补价"，**不计入合计**（避免虚增）。
5. 任何一次请求可凭 `X-Relay-Trace-Id` + `X-Relay-Mode` 回溯"被哪层处理"（透明性）。

### 5.4 我方（运营/销售）视图

- 客户级 WTCS 排行（识别高价值客户 → 续费/提额）、ADR 漏判 TOP（补规则）、OH/误拦告警（护栏）、上游 wasted-token 排行（调路由权重）、`relay.cost.unknown` 清单（补价格配置）。

## 6. 关键结论速览（供主理人汇编）

1. **市场**：AI/LLM 网关市场增速收敛于 **26%–29%**，亚太最快、Agent 网关最快；但**报告口径跨度达 ~25×**，只能引用增速与结构，**SOM 必须自下而上自测**。
2. **可对账指标**：§2 冻结 9 项主指标 + 2 项护栏；**最关键 3 个对账指标**为
   ① **无效 token 成本节省额 WTCS** = `[WastedCost_C − WastedCost_E] + [CacheSaved_E − CacheSaved_C] + [RetrySaved]`（¥/年）；
   ② **自动恢复数 ARR** = `Σ relay.reduction.recovered_requests`；
   ③ **无效重试数 DR** = `Σ relay.retries.duplicate`（60s 同 payload，单副本口径）。
3. **实验**：主设计为**同层请求级随机 A/B**（主终点=无效重试率相对降 20%，**每组 ≈6,750 请求 / 合计 ≈1.35 万**）；辅设计为 **free 纯管道 vs pro 全降损**的前后+分层对比做价值核算（客户级只报 bootstrap CI）；**观测窗口建议 4 周（1 周洗牌 + 3 周观测），最低 2 周**。
4. **定价路径**：**5 个阶段**（S0 埋点 → S1 基线 → S2 价值量化 → S3 溢价反推 → S4 区间与试点）；结论为 **Pro 溢价 = WTCS × 捕获率 − 我方成本**，且**降损节省额（个位数百分比）不足以单独支撑高订阅价**，Pro 应以"额度+SLA+可观测"为主锚、"可对账节省额"作价值证明。
5. **看板**：客户面报表以"计数 × 单价 = 金额"三段式呈现并支持 CSV 复算，直接回应"客户能不能自己算出省了多少"。
