## 1. 现有页面与模块盘点

### 1.1 路由与导航事实（源码为准，非 README）

- **入口**：`main.tsx` → `App()`，`view.value` 从 `location.hash` 解析（`state.ts#hashTab`）。
- **页签注册表**（`state.ts#TABS`，共 **11 个** id）：
  `ov 总览 / met 指标 / users 客户 Key / ch 上游 / kb 知识库 / agent Agent / agentchat Agent 对话 /
  ledger 请求账本 / diag 排障 / ops 运维 / trust 信任`。
- **侧栏分组**（`state.ts#NAV_GROUPS`，四组）：
  - 监控：总览、指标、请求账本、排障
  - 配置：客户 Key、上游
  - 智能：知识库、Agent、Agent 对话
  - 系统：运维、信任
- **路由形态**：`/admin#<tab>` 或 `/admin#<tab>/<anchor>`（如 `#diag/cheat-reason`），支持刷新/收藏/分享停留原处。
- **全局壳层**：`TopBar`（版本号、时钟、数据新鲜度、主题切换、刷新、退出）+ `SideNav`（分组导航 + 窗口/自动刷新/刷新间隔）+ `main` + `ToastHost` + `DrawerHost`；`Esc` 先关抽屉再关移动侧栏。
- **登录门**：`Login` 组件走 `POST /admin/api/login`，令牌存 `localStorage`，401 自动登出。

> ⚠ **盘点纠偏（供下游注意）**：`project/README.md` §8 文字描述为「八个页签（总览/指标/客户 Key/对账/账本/排障/运维/信任）」，与源码实际的 11 个页签**不一致**——README 提到的「对账」并没有独立页签（对账能力散落在「客户 Key」页的 CSV/JSON 导出与「请求账本」页的导出里），而源码多出「知识库 / Agent / Agent 对话」三个页签。**以源码 11 个页签为准**，README 待修订。

### 1.3 现有交互模式总结（供设计系统统一）

- **主视图都是表格 + 右侧抽屉详情**：列表主视图常驻，详情按需展开，`Esc`/点遮罩关闭。
- **自动刷新策略分级**：只读页默认 15s 自动刷新；客户 Key 与表单页**刻意不刷新**；失败按 `isRetriable` 分级（脚本错误不重试、可恢复降频）。
- **写操作防护**：不可逆动作集中在「更多…」抽屉并把后果写在按钮前；每次写操作进 `relay_event` 事件流可审计。
- **数字列右对齐 + `tabular-nums`**；`MiniBar` 呈现额度/预算进度。
- **骨架屏首载 + 渐显**避免闪屏；`CSV_BOM + CRLF` 保证 Excel 直开。
- **统一响应式**：移动端侧栏抽屉（`navOpen`）+ `mobile.css`。

## 2. 业务目标

把 api-relay 从「自托管工程师工具（命令行 + 内部看板）」升级为「可对外运营的聚合中转模型 API 平台」。目标必须可量化、可验收。

### 2.1 目标拆解

| 编号 | 目标 | 可量化验收标准 | 现状差距 |
|---|---|---|---|
| G1 | **客户自助**：客户不依赖运营手工转发配置即可拿到 key、查用量、看错误 | 新客户从申请到首次成功调用 ≤ 10 分钟；自助渠道覆盖 ≥ 80% 的用量查询 | 现无自助注册/审批；key 由管理员在面板手工创建 |
| G2 | **套餐可售卖**：套餐（分层×模型白名单×预算闸）作为一等商品在平台上呈现与售卖 | 套餐目录页可展示 ≥ 3 个在售套餐；套餐→key 的映射 100% 由 `allowedModels` 圈定 | 套餐逻辑代码已实现（§9），但**无面向客户/销售的套餐目录与购买入口** |
| G3 | **成本可控**：客户预算不超、平台成本可视 | 超预算请求 100% 返 402；每客户成本与牌面价差（毛利）可在一个页面读出 | 有 `quotaCny` 闸与 `costCny/listCostCny`，但无面向运营的毛利/成本看板 |
| G4 | **合规清晰**：可对外声明"不改写成功响应、不落正文、可自证" | 信任页红线 100% 有测试落点；可导出审计事件；客户可自助对拍 HMAC | 信任页素材已具备，但**混在内部运维面板中，缺客户面正式呈现与合规导出** |
| G5 | **运营可值守**：一人可管多客户、多上游，异常有明确处置路径 | 单次事故定位（从告警到根因）≤ 5 分钟；值班摘要自动化 | 值班摘要、横幅、排障页已具备，基本达成 |
| G6 | **可扩展性**：非 OpenAI 协议可归因、模型/上游可热维护 | 新增一个上游仅需改一行配置；非 OpenAI 上游返回可归因错误而非静默失败 | 架构已支持（`auth.format`、归因六大错误体）；Anthropic/Gemini 原生仅留位 |
| G7 | **二次开发可交付**：本次交付为设计原型（Design Proto），而非新后端 | 产出 01~05 五份文档 + 可打开的高保真 HTML 原型 + 审查放行结论 | 本工坊目标即交付原型，不改动运行时代码 |

### 2.2 升级的本质

- **从"能用的网关"到"能卖的网关"**：技术能力（聚合/熔断/降级/分层）已具备，缺的是**面向客户与销售的产品化外壳**（套餐目录、自助门户、账单、只读用量视图）。
- **从"内部看板"到"双面产品"**：同一套数据要拆成「运营面（现有面板）+ 客户面（自助只读）」，二者权限与信息密度不同。
- **从"工程师语言"到"客户语言"**：信任页、错误码表已写出客户语言，需系统化为可对外发布的开发者文档。

### 2.3 本部分元信息

- **目标**：把模糊的"继续二次开发"翻译成 7 条可验收的业务目标。
- **输入**：`README.md` §6/§9/§11、`readme/README.md`、`docs/research/*`（商业化推演引用）。
- **产出物**：§2.1 目标-验收-差距表。
- **关键决策**：**本次交付定位为「设计原型（Design Proto）」**，不新增/修改后端能力；所有 G1–G6 通过前端与信息架构的重新设计来"暴露"与"产品化"已有能力，避免越界改动核心链路。
- **风险与待办**：① G2/G3 涉及"钱"，需与用户确认定价与毛利口径后才能在原型上落数值；② 若用户期望本次交付包含真实后端改造，需重新界定范围（见 §7 Q1）。

## 3. 用户角色

| 角色 | 职责 | 核心诉求 | 痛点（现状证据） | 典型任务 |
|---|---|---|---|---|

| **客户开发者（Client Dev）** | 把 `base_url` 指过来集成、调 API、处理错误、查用量 | 拿 key 即用；出错时知道"下一步做什么"；能自助查用量与自检 | **无客户面自助入口**：所有查询靠运营转发；whoami 自检在管理面板里（需管理员令牌） | 首次接入（OpenAI SDK 两行改）、处理 429 退避、查本周期用量、key 失效自检 |
| **财务 / 销售** | 对账、收款、跟进续费、评估毛利 | 每客户本周期消耗与预算、续费提醒、可导出对账单 | 现有 CSV/JSON 导出偏原始读数，缺"账单"形态与币种口径说明；无销售视角的套餐/毛利视图 | 导出客户用量对账、核对超预算客户、跟进"将耗尽/将过期"客户 |
| **审计 / 合规** | 核对"不改写、不落正文、可自证"是否成立；留存操作审计 | 红线可验证、事件可导出、正文不留存有据 | 信任页与事件流已具备，但需管理员令牌且混在内部面板 | 抽查事件流、验证 HMAC 自证命令、导出审计事件 CSV |
| **（隐含）运营/值班自动化** | 用值班摘要交接、用 Agent 巡检沉淀知识 | 摘要可一键复制、异常自动提示 | 值班摘要已可复制；Agent/知识库属内部能力，与对外平台边界需厘清 | 生成值班摘要、查看 Agent 最新决策、把结论写入 KB |

### 3.2 本部分元信息

- **目标**：把"用户"从抽象变成有职责、有诉求、有痛点、有典型任务的具体角色，并给出权限矩阵。

- **关键决策**：显式引入**财务/销售**与**审计/合规**两个非工程角色作为一等公民，因为平台化后"钱"与"合规"是核心诉求；把「客户开发者」的自助能力定为本轮最大缺口。

## 4. 核心场景与用户旅程

> 每条场景给出：触发 → 步骤 → 期望结果 → 现状缺口。至少 6 条。

### 场景 1：客户注册领 key → 调 API → 看用量账单 → 套餐升级（客户主线）

1. 客户在平台（或经销售）选择套餐（如"MiMo 套餐"：`mimo-v2.5-pro` 主用 + 兜底，¥10 预算）。
2. 平台/管理员签发 key，客户**自助**看到 base_url、可用模型、SDK 示例、端点、错误码、自验命令。
3. 客户用 OpenAI SDK 只改两行（`base_url` + `api_key`）发起首次调用。
4. 客户在**自助门户**查看本周期 token/成本/预算余额与近 1h/5h/24h 用量。
5. 额度/预算将耗尽 → 平台提示 → 客户申请升级套餐 → 新 key 白名单与预算更新。

- **期望结果**：全程 ≤ 10 分钟，运营零人工介入（除审批）。
- **现状缺口**：步骤 2/4/5 全部缺失客户面入口；接入包文案已存在（`customerPackage`）但只能由管理员生成转发。

### 场景 2：运维上游熔断处置

1. 总览横幅/上游页显示某上游错误率突告或熔断中。
2. 运维到「请求账本」点开失败条看步骤时间线与归因，分清"配额限流（等一会/降权）"还是"真故障（摘除）"。
3. 若真故障 → 上游页「摘除」（流量立即切换）；若配额问题 → 去厂商控制台充值后「清熔断」。
4. 观察半开恢复：冷却到期试探一次，成功即清零计数切回主用。

- **期望结果**：故障期间客户请求仍 200（横向兜底），恢复自动被发现。
- **现状缺口**：处置路径分散在四页；可整合为「事故处置」聚合视图（新增）。

### 场景 3：管理员密钥审批与轮换

1. 客户申请 key 或申请扩容 → 管理员审批（签发或调整白名单/预算/有效期）。
2. 明文 key **只显示一次**，管理员生成"客户接入包"转发（或客户自助领取）。
3. key 泄露 → 轮换（旧 key 立即失效）；或临时停用（可恢复）。

- **期望结果**：审批留痕（进 `relay_event`）；明文不落库（服务端只存 sha256，指纹前 8 位）。
- **现状缺口**：无独立"审批"流程与状态（待处理/已批准/已拒绝）；轮换/停用已具备但缺审批队列。

### 场景 4：财务账单对账

1. 财务按周期导出各客户用量（token/成本/预算）。
2. 与收款记录比对，找出超预算、将耗尽、将过期客户。
3. 跟进续费/提额，导出对账单发给客户。

- **期望结果**：一屏出"谁是本周期该收钱的、收多少、还差多少"。
- **现状缺口**：`Keys.tsx` 有 CSV/JSON 导出，但**无账单形态**（无期间汇总、无币种/含税口径、无对账单模板）。

### 场景 5：新客户自检排障

1. 客户报"API 全 401 / 调不通"。
2. 客户**自助**粘贴手上的 key 做自检（whoami）：有效/已禁用/已过期/非本网关签发。
3. 客户按错误码表（401/403/404/429/502/503）自助判断是"换 key""开通模型"还是"退避重试"。

- **期望结果**：客户不打扰运营即可定位"是 key 问题还是模型问题还是上游问题"。
- **现状缺口**：whoami 与错误码表都存在，但 whoami 在**管理面板内**（需管理员令牌），客户面不可达。

### 场景 6：容量告警响应

1. 容量指标（进程在途请求、上游并发、错误率、上游停用/熔断数）触发告警。
2. 运维到「指标」页看原始读数（在途持续偏高=上游慢；令牌失败>0=有人在试管理令牌）。
3. 处置：扩容上游/加 key 槽、限流降档、或摘除异常上游。

- **期望结果**：比错误率更早发现"要出事"的信号。
- **现状缺口**：`Metrics.tsx` 已具备原始读数，但**无告警阈值与推送**；容量与业务（客户/套餐）未关联。

### 场景 7（补充）：审计合规核验

1. 审计抽查事件流（key 轮换/吊销/降损开关改动/上游熔断），导出 CSV。
2. 核对信任页四条红线与其测试落点，跑自助 HMAC 对拍命令。

- **期望结果**：可向客户/监管证明"不改写成功响应、不落正文、可自证"。
- **现状缺口**：需管理员令牌；事件表的自动清理策略与留存周期需在合规页面显式声明。

### 场景 8（补充）：值班交接

1. 值班结束，点「一键值班摘要」生成九行纯文本（总体/上游/模型/失败主因/需处理/降损层/Agent/平台状态/Key 预警）。
2. 粘贴到 IM/邮件完成交接。

- **期望结果**：交接零遗漏。**现状已实现**（`buildShiftBrief`），可作为平台"每日运营简报"的基座。

### 4.1 本部分元信息

- **目标**：用 8 条端到端旅程锚定"平台化"要补齐的交互链路，防止原型只做静态页面。
- **输入**：§1 页签现状（尤其 `Keys.tsx` whoami/接入包/轮换、`Overview.tsx` 值班摘要、`Providers.tsx` 熔断、`Diag.tsx` 归因目录）。
- **产出物**：§4 场景 1–8 + 各自现状缺口。
- **关键决策**：以**客户主线（场景 1）**为原型的第一优先级，因为它覆盖了最大的产品化缺口（自助入口/账单/套餐升级）。
- **风险与待办**：① 场景 1 的"自助注册"若用户选择不做（见 §7 Q2），则场景 1 需降级为"销售协助开通"；② 场景 6 的告警推送涉及后端，本轮仅在原型表达阈值与态势。

## 5. 功能边界

### 5.1 做（本轮设计原型要覆盖）

- **客户面产品化**：套餐目录页、自助/半自助 key 领取与接入包、客户用量与账单只读视图、客户自助自检（whoami 客户版）、开发者文档/端点/错误码页面。

## 6. 约束条件

### 6.1 技术约束（硬）

| 项 | 约束 | 对设计的影响 |
|---|---|---|
| 前端框架 | **Preact + signals + Vite 6** | 组件设计须为 Preact 兼容（含 `@preact/signals`）；不可引入框架级重依赖 |
| 状态管理 | `signal`/`useSignal` + 局部 `useState`/`useEffect` | 全局状态集中在 `state.ts`；设计须沿用 signal 模式 |
| 运行时依赖 | **0 个第三方运行时依赖**（仅 `node:http/crypto/sqlite`） | 前端尽量零 CDN 依赖（现有面板即零 CDN、内网可用）；图标用文本符号 |
| Node 版本 | **≥ 22.5**（用到 `node:sqlite`） | 部署与工具链边界 |
| 语言 | TypeScript 5.6 strict，编译到 ESM | 类型严格，原型示范须类型正确 |
| 构建产物 | `dist-admin/`（前端已随包交付、免构建） | 原型可参考/复用现有构建结构 |
| 存储 | SQLite（WAL，控制面）/ 内存可切换 | 数据形态受限于现有表结构 |
| 请求层 | 统一走 `api()`（30s AbortController）；长任务（AgentChat）例外自定义 180s | 新增页面须遵循统一请求层与超时策略 |

### 6.2 安全约束（红线，不可破）

- **不改写成功响应**（红线 1）：2xx 与 SSE 逐字节透传；唯一受控例外是 model 回显改写。
- **错误只增不改**（红线 2）：保留上游 `message`/`code`，归因只作附加字段/响应头。
- **fail-open 不可破**（红线 3）：治理层异常静默回退；唯一 fail-closed 是鉴权。
- **不落用户正文**（红线 4）：默认不存 prompt/completion 正文；指纹用 HMAC 截断 16 字符。
- **明文 key 只显示一次**：服务端只存 sha256，接口永不回显明文（有测试断言）。
- **预算按钱算**：`quotaCny` 超预算返 **402**（不是 429），避免客户端把"没钱"当"限流"无效重试。
- **统一响应头**：`X-Relay-Mode` 回显本次被哪层/哪套开关处理（透明性）。

### 6.3 合规约束

- 归因作为**给客户端的稳定契约**（蓝字 reason 可程序化分支）。
- 事件流可审计、可回溯（每次写操作进 `relay_event`）。
- 信任页四条红线每条对应测试落点，可对外公示。
- 公开只读端点（`/v1/quota`、`/v1/panel`）默认仅 `127.0.0.1`，远程需显式开 `server.publicQuotaRemote` + 反代白名单。

### 6.4 兼容约束

- **OpenAI 协议兼容**：任何 OpenAI SDK 只改 `base_url` + `api_key` 即可用；成功响应零附加字段。
- **非 OpenAI 上游可归因**：六种错误体形态（标准 OpenAI / 智谱 GLM / Kimi / SiliconFlow / OpenRouter / HTML）均须解析；非 OpenAI 兼容返回可归因错误而非静默出错。
- **Anthropic / Gemini 原生仅留实现位**：Anthropic Messages 兼容**仅 agnes 系模型**；mimo/step 系走该端点会 404。
- **错误体形状统一** `{ error: { message, type, code } }`；缺失字段才补齐。

### 6.5 本部分元信息

- **目标**：把技术/安全/合规/兼容四类硬约束显式化，作为设计系统的"不可越界清单"。
- **输入**：`README.md` §1/§6/§7、`DESIGN.md` 红线、`ARCHITECTURE.md`、`DECISIONS.md`、`views/*.tsx` 中的请求层与文案。
- **产出物**：§6.1–§6.4 约束表。
- **关键决策**：把"零运行时依赖/no-CDN"与"Preact signals"提升为设计系统的强制前提（下游阶段2 选型必须兼容）。
- **风险与待办**：① 若下游引入带 CDN 字体/图标的方案，会破坏"内网可用/零 CDN"承诺，必须在阶段2 复核；② `trustProxy` 保留字段当前无作用（不记客户端 IP），涉及合规声明时需说明。

## 附录 A · 给下游（设计系统专家，阶段2）的关键约束提示

1. **调性锁定**：**Tech Utility（技术工具感）** 为首选——等宽字体、数据密集、深色调；须与现有管理面板（暗色 + `tabular-nums` + 文本符号图标）视觉延续，不可突变。
2. **框架硬约束**：设计令牌与组件必须 **Preact + signals 兼容**；**零 CDN 依赖**（内网可用），图标优先文本符号/内联 SVG。
3. **双面设计**：同一套令牌需同时服务"运营面（高信息密度）"与"客户面（低密度的自助/文档）"——密度策略需在令牌层可切换。
4. **不可越界的红线**：任何组件不得暗示"改写成功响应/缓存/去重/Agent 平台"能力。
5. **关键组件清单（复用优先）**：表格（右对齐等宽数字）、右侧抽屉、MiniBar 进度、Chip 状态标签、KPI Tile、骨架屏、Toast、状态横幅（banner）、归因卡片。
6. **状态色语义**：`ok/warn/err` 三态必须与现有面板语义一致（如预检降级放行=warn、零 token 成功=err 温度计）。
