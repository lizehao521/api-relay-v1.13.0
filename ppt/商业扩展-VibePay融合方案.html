行业判断 Vibe Coding 正在变成 Vibe Business

Vibe Pay 的定位是「让每一个 AI 创作者，都能更轻松地把应用做成生意」：一个产品覆盖网页与 App，商品、订单、权益三类管理及后台默认提供，支持次数包 / 积分包 / 时长包 / 买断四种收费方式。
—— 支付宝 AI 付 · Vibe Pay 产品页（2026-11 访问）
变化 ①
交付即收费

AI 应用从「能用」进入「值得付」，收费能力从附加项变成上线前置条件。

变化 ②
体验可以按时段

除 Token 次数包外，也可把云端图像生成做成「一人一小时」的体验权益。

变化 ③
权益需要被核销

「付了钱」不等于「服务已交付」，必须有权益查询、放行与使用后核销的闭环。

结论：支付解决「收钱」，权益内核解决「收钱之后怎么交付、怎么扣减、怎么对账」——这恰好是 api-relay 已有的能力。

缺的那一块：钱怎么进来 收款与订单

api-relay 已经能回答「这次调用该扣多少」，但还不能回答「这笔钱从哪来、对应哪笔订单」。

  • 缺少商品：额度包 / 次数包 / 时长包的可售定义
  • 缺少订单：支付成功回调、幂等、退款与撤销
  • 缺少权益放行：支付完成 → 订单确认 → 对应 Token / 算力权益到账
  • 缺少算力调度：GPU 会话隔离、排队、时限、自动释放与成本计量
  • 缺少结算对账：平台代收 / 直收商户两种资金流
为什么不自建支付
自建收款是最贵的那部分

网页支付、App 支付、签约、对账、退款、风控、发票——每一块都要独立建设与合规投入。Vibe Pay 的「智能收款套件」把这些默认提供，api-relay 只需对接权益与交付。

定位：不重复造支付轮子，把工程优势集中在「权益内核 + 计量结算」。

对应 Vibe Pay 的四步接入：① 商品信息确认与收费配置 ② 付费入口与购买链接 ③ 购买后权益校验与访问放行 ④ 使用后权益核销。

算力供给

关键不变量：回调验签和订单幂等通过后才发放权益；算力会话按人、按时限授权，到期 / 空闲即释放。M0 只有 Token 券，以上支付与 GPU 调度均为后续建设。

单商家供给与成本边界 自供优先，代供可选

商家自供
商家控制模型与成本

商家自己承担模型或设备成本；平台收取约定的软件、部署或运营服务费，不替商家垫付上游资源。

平台代供 · 可选
按时段提供云端出图
顾客→商家收款→平台云算力服务

可售「每人 1 小时」云端图像生成体验，A10 作候选配置；云资源费用、服务费及退款责任须单独约定。

  • 供给边界：商家自供 Token、商家自供算力、平台云算力或暂不提供 AI，均作为可选择的服务模式。
  • 安全边界：供应商密钥留在服务端；GPU 会话按用户隔离并设置时限，结束后释放资源。
  • 资金边界：收款主体、退款及服务责任按支付渠道能力和合同确认；不把平台分账或合规状态当作已实现。

一人一小时出图

单会话贡献 = 售价 − A10 实际租用时长成本 − 存储 / 流量 / 支付等费用；按实际云厂商报价核算，不预设固定低价。

平台模型
软件服务 + 可选代供

自供模式收软件 / 部署服务费；代供模式再核算云算力或 Token 成本、利用率、退款与闲置损耗。

收入项计价基础可复算依据
门店软件 / 部署费按门店 / 服务周期合同、门店数、服务记录

权益核销实际领取 / 使用记录redemption + 订单关联

A10 型号、云厂商、地区、计费粒度和实例利用率都会改变成本；先询价并实测单次任务，再定售价。以上不构成收益承诺。
