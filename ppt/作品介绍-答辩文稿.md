## 开场（P1 封面）

各位评委好，我们是「落幕」队，作品是 **api-relay —— 智能体基础设施层**（OpenAI 兼容的模型 API 聚合中转站 + 内嵌传话层工程降损）。**我们没有再造一个 Agent，而是做所有 Agent 都要站的那层地基。**
一句话价值主张：**它卖的不是 token，是「错误对 Agent 可执行」**——成功响应逐字节透传，错误路径翻译成可执行动作。三个词概括：**错误可执行 · 数据可信 · 损耗可度量**。

## 一、场景分析（P2–P3）

**痛点**：传话层的损耗，没人负责。引用某头部中转平台官方文档原文——"一次 400 错误会消耗数倍的限流配额"。**失败是有成本的，但没人把这个成本告诉用户**。

我们处在两层"传话层"之间：Agent 是模型↔环境的传话层，中转站是客户端↔上游的传话层。问题有三个：错误码各家有各家的方言；Agent 拿到 429 不知道退避还是换 key；损耗没有基线、无法度量、无人优化。

**谁在承担成本**：AI 应用开发者（错误处理代码占比可观、重试逻辑每家重写一遍）；企业接入方（路由/限额/熔断/账目全要自建）。**现有方案只做"转发"，"错误可执行化"仍是空白。**

## 二、方案设计（P4–P5）

**降损三件套，建在核心链路上**：
- **P2 调用前预检**：畸形 `tool_calls`、超长输入等"必然被拒"的请求在上游之前拦下，省一次往返与计费；
- **P3 失败时归因**：raw error → `{failure_reason, suggested_next.action, recoverable, retryAfterMs}`，**15 类归因 × 11 个可执行动作**；
- **P8 持续量化**：归因投递率、自动恢复、无效重试、治理层自身开销——**没有度量就没有优化**。

关键区分举例：429+余额不足 → `quota_exhausted + top_up_balance`（不可重试），且余额不足回 **402 而非 429**——不让 Agent 浪费一次重试。

**技术选型与刻意边界**：Node ≥22.5 + TS strict（ESM，内置 `node:sqlite`，单二进制部署）；**运行时依赖 0 个**（供应链攻击面为零）；SQLite(WAL) 存储；Preact+signals+Vite → 纯静态产物。**刻意不做**（能说清边界的团队才可信）：不改写成功响应、不做响应缓存、不做 Agent 平台、不 fork AGPL。

## 三、核心功能（P6–P9）

1. **OpenAI 兼容网关**：`/v1/chat/completions`（SSE）、`/v1/embeddings`、`/v1/completions`、`/v1/models`；多上游聚合（权重路由·熔断·指数退避+抖动·自动兜底）；分层计费（free 层纯管道，错误体与上游**字节一致**）。**信任原则**：成功响应逐字节透传——"我没有动你的数据"。
2. **内嵌管理面板（零配置）**：总览/指标降损基线/**速查 key 诊断**/账目/信任/用户等 17 页；key 只存指纹 `sha256("relay-key:"+key)` 前 8 位；demo 模式免令牌，**3 分钟从克隆到看见面板**。
3. **客户端 SDK：一行重试**：`autoRetry()` 对可重试失败按 `retryAfterMs` 退避+抖动重试，不可重试立即抛出且自带归因卡片；**15 项单测**、**零依赖**、一行接入。
4. **平台化四件套（v1.11.0 新增，已上线）**——把"单点网关"升级为"可面向多团队/多租户运营的平台"：
   - **批次1 多租户 / RBAC**：租户注册表（default + 自定义）、角色矩阵（owner / operator / viewer）、权限点细分（`billing.write` 与 `keys.write` 职责分离）、租户谓词过滤 + 审计留痕；
   - **批次2 计费账务**：套餐目录 `PlanRegistry`、账单 `bills`、对账 `recon`（可导出 CSV/JSON）——**计数 × 单价 = 金额，可复算**；
   - **批次3 分布式状态原语**：`SharedStateStore` 并发闸门 + 控制面文档持久化（`control_doc`），engine/keys/pool 接入排队语义——**仅注入共享后端时生效，默认零回归**；
   - **批次4 协议适配**：`adapters` 互译层 + **REQ-03 流式 mid-stream error 帧**；Anthropic `/v1/messages`、Gemini `generateContent` 入站接线（opt-in，默认关闭）。

   > 这四件套对应"中转站 → 平台"的跃迁：别人停在"转发 + 限流"，我们补齐了**租户治理、可复算账务、多实例状态原语、多协议入口**。

## 四、码道应用成果（P10–P11）

**我们不是单窗口问答式用 AI，而是把码道当作带角色分工的虚拟研发团队**：team-leader 拆解任务书 → sdk-engineer（代码生成）→ audit-executor（真机核查）→ code-reviewer（代码审查）→ final-verifier（独立放行），**实现→核查→审查→放行四段闭环**。设计与竞品调研阶段另引入 5 阶段专家链（需求发现→设计系统→原型构建→质量审查→导出交付）。

关键数字：**42 个工作区留存会话、累计 ≈56,975 万 tokens（约 5.70 亿）、9 份任务书落盘、55 条真机核查记录、505 项测试放行前独立复跑全绿**。时间跨度 2026-10-18 ~ 10-28，全流程覆盖：环境排障 → 需求调研 → 架构裁决 → 代码生成 → 真机核查 → 代码审查 → 质量门禁 → 文档生成 → 批次收尾 → **平台四件套落地 + 生产部署**，**每一环都有落盘文档，可追溯、可复现**（证据链见 `codearts_proof/`）。

**Prompt 工程：任务书即接口**。我们的任务书有六段固定结构：角色声明 → 硬约束前置 → 事实来源 → API 形状 → 禁止事项 → 验收标准。三层反幻觉防线：字段名从源码核实、真机执行、独立复跑。**如实记录文化**：55 条核查中 3 条不符、4 条无法验证，原文保留不粉饰。实证效果：SDK 任务**一次通过审查（APPROVE），零返工**。

## 五、创新亮点（P12）

1. **错误可执行化**：把"失败对 Agent 可执行"作为第一设计原则（竞品逐行比对，file:line 级证据存档）；
2. **同价承诺**：free 层错误体与上游字节一致，降损不成为加价理由；
3. **防彩虹表指纹**：`sha256("relay-key:"+key)` 域前缀（裸哈希可被字典反推）；
4. **零运行时依赖**：部署只需一个 Node 二进制；
5. **损耗可度量（P8）**：连"治理层自身开销"也纳入量化——**降损层自己也要被降损衡量**；
6. **平台化四件套（本版新增）**：多租户/RBAC + 可复算账单 + 并发闸门原语 + 协议互译层，四者组合在同类中转项目中罕见——多数项目止步于"网关 + 面板"。

差异化总结：**别人卖转发，我们卖"错误发生后的确定性"，再把这份确定性做成可运营的平台。**

## 六、落地规划（P13）

**当前**：生产环境运行中，服务真实客户（分层 key、额度、账目全在用）；**多租户/RBAC、计费账务、协议适配已完成并部署上线**（v1.11.0），**配置主档/阶梯分离 + 中文档位链名（旗舰/平衡/极速/推理）已上线**（v1.12.0），**商户 token 券闭环 M0 已上线**（v1.13.0）；**mock 模式保证评委零密钥复现全部功能**（`bash demo.sh`）。
- **近期**：华为云深化——ECS + ELB 部署方案；对接**华为云 ModelArts 盘古模型**作为上游池成员；
- **中期**：平台化深化——开放自助注册、按量计费线上对接、多实例共享 state（Redis）、自助开票与对账导出；
- **远期**：标准输出——**降损基线开放 API**，让"中转站质量"成为可比较的行业标准。
- **商业模式**：标准层订阅 + Pro 层按量；**降损数据本身即是企业客户的采购理由**。
